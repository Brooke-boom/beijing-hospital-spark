## 一、30 秒电梯陈述（答辩开场，背下来）

> 我的课题是《基于Spark的北京市医疗机构资源整合与多维筛选可视化系统》。
> 它解决的实际问题是：北京市医疗机构数据分散在多个公开渠道、口径不一，公众想按"家附近的三甲医院、能看某个专科"这类条件找医院时，缺乏一个统一的查询入口。
>
> 系统整合了 **9,678 家**医疗机构，用 Spark 做 **ODS → DWD → DWS → ADS 四层离线数仓**，产出写入 MySQL，由 Flask 提供查询接口，ECharts 做可视化。
> 功能上支持 **七维筛选、五种排序、AI 对话式筛选（单一 AI 入口·四模式）**，以及一个零依赖的离线大屏。
> 数据可信度方面，我以市医保 A 类定点名单 58 项为基准做了交叉验证，**覆盖率 100%、等级标注正确率 100%**。

**关键点**：开场就给出"数据量 + 技术栈 + 功能 + 可信度证据"四件套，30 秒内建立可信形象。

## 四、五个技术亮点（每个都能展开讲 1 分钟）

### 1. 四层数仓分层（不是为分层而分层）
- **ODS**：原样落库，保留原始数据可追溯；
- **DWD**：去空去脏、统一编码、**join geocode_cache 补全经纬度**（这是最有价值的一步）；
- **DWS**：按区域/等级/类型/科室 4 维聚合，直接供大屏图表使用；
- **ADS**：`ads_inst_search` 宽表（40 字段）+ 3 张概览表，Flask 直接查，不 JOIN。

> 被问"为什么分四层"：分层是为了**职责隔离**——上游源数据变了只改 DWD，图表需求变了只改 DWS，接口字段变了只改 ADS，互不影响。

### 2. 数据可信度可验证（这是最强的差异化）
- 以市医保 A 类定点名单（2026-08-08，58 项）为基准：**覆盖率 100%、等级正确率 100%**；
- 三批联网核实共修正 13 家次等级；
- 发现并纠正"因机构更名导致的匹配失败"（空军总医院→空军特色医学中心等 5 条），**避免了凭空多出 2 家重复机构**；
- 过程全部记录在 `docs/数据联网核实报告.md`。

### 3. "宁缺勿伪"的数据取舍（体现工程判断力）
- 床位数覆盖率仅 **1.2%（116/9678）**，取值异常聚集（"20"出现 34 次），判定为估算值 → **彻底移除展示与评分**；
- 评分权重由 `0.4等级+0.3距离+0.2床位+0.1科室` 重构为 **`0.5等级+0.3距离+0.2科室`**；
- 宁可少一个维度，也不用假数据撑场面。

> 这一段特别建议主动讲，因为它体现了"发现问题—量化分析—做出取舍"的完整工程决策链，比堆功能更能拿分。

### 4. 查询索引优化（可量化）
- Spark 建表的字符串列是 TEXT，MySQL 不允许直接建索引 → 用**前缀索引**（UTF-8 汉字 3 字节，取 24/60）；
- 建 `idx_inst_search_main`(district, level_norm, category) 后，EXPLAIN 扫描行数 **9,777 → 33**；
- 注意：`mode="overwrite"` 会 DROP+CREATE 表，**每次跑完 ETL 必须重跑 `etl/create_indexes.py`**。

### 5. 零依赖单文件大屏（最实用的工程巧思）
- `build_spa.sh` 把数据快照 + ECharts + HTML/CSS/JS 全部内联进一个文件（6.5MB）；
- 老师/面试官**双击就能打开**，不需要 Docker、不需要数据库、不需要联网；
- 代价：文件较大、数据更新需重新构建 → 作为"快照交付版"，联调版仍走 Flask + MySQL。

## 五、高频追问 Q&A（16 题）

**Q1：数据才 9,678 行，用 pandas 就够了，为什么要用 Spark？**
> 诚实回答：本课题规模下 Spark 的计算优势并不明显，选择它有 3 个理由——① 采用与生产一致的分层架构与工程规范；② 数据量增长到百万/千万级时可平滑扩展，无需重写；③ 通过 Docker Compose 完整实践了分布式环境搭建。这是**工程实践价值**大于**性能价值**，我在论文中也如实说明了这一点。

**Q2：四层里哪一层最难？**
> DWD。难点是坐标补全：地址文本质量参差（含"甲1号"等），要 join geocode_cache 并标记精度等级（区县/街道/门址）。目前 55.7% 仅到区县级，受地址本身模糊限制，再跑 API 提升有限。

**Q3：数据从哪来？怎么保证真实？**
> 全部来自公开渠道（市卫健委、医保局、各区政府网站等），无虚构模拟数据。以 A 类名单 58 项交叉验证，覆盖率与正确率均 100%。对真实性存疑的字段（床位）直接移除而非填充。

**Q4：你的 9,678 家和官方 12,298 家差 2,509 家，是不是数据不全？**
> 不是数据错误，是**统计口径不同**。差额几乎全是基层机构（村卫生室 2,891 + 社区卫生服务站 2,143），官方全量口径包含它们。而本系统聚焦"找医院看病"场景——**医院类 732 家 vs 官方 765 家，吻合度 95.7%**，核心目标对象覆盖良好。补基层反而会稀释等级分布与科室覆盖图表。

**Q5：三级 180 家 vs 官方 146 家，是不是标多了？**
> 官方 146 是特定统计口径（含部队医院等认定范围不同）；本系统经三批联网核实，逐一比对权威来源，A 类 58 项等级正确率 100%。差异源于纳入了部队医院、民营三甲及新晋级医院。

**Q6：为什么删掉床位数据？**
> 覆盖率 1.5%，且取值聚集（"20"出现 34 次、"599"出现 10 次）明显是采集占位/估算值。留着会让 98.5% 的机构显示"—"，还在评分里占 20% 权重空转。所以移除，权重由等级承接。

**Q7：Haversine 是什么？为什么在 SQL 里算？**
> 球面两点距离公式，比平面欧氏距离准确。放在 SQL 里是为了直接支持"按距离排序"和"N 公里内筛选"，避免把全表拉到应用层计算。

**Q8：系统的默认排序（条件匹配度）是怎么设计的？为什么没有加权评分？**
> 早期版本做过加权评分，后来**主动移除了**：本系统的数据是机构资源名录，没有质量结果数据，任何加权分数都会被误读成"医院好坏评分"。所以现在是"严格筛选"语义——结果须满足全部条件，匹配度统一为 1；并列时按**等级（高→低）→ 科室收录量（多→少）→ 机构名称**裁决，用的都是数据集真实收录字段。排序共有 5 种：条件匹配度 / 距离 / 等级 / 科室收录量 / 机构名称。

**Q9：智能筛选调用大模型了吗？**
> 分两条链路。**机构筛选**的主路径是纯规则引擎（词表 + 正则，零延迟、零成本、可离线、可复现），规则零命中时才调 Agnes 做兜底解析（只许输出条件，禁止输出机构名与数字）。**问诊导诊 / 就医建议 / 医院选择**三个 AI 模式走 `POST /api/ai/chat` 调 Agnes，但回答被硬约束在当前真实筛选结果（facts 前 10 家）内。

**Q9.1：为什么要对医疗类输入做拒答？这算不算功能缺失？**
> 不是缺失，是**边界**。本项目的数据是"机构资源数据"（9,678 家机构的公开名录、等级、科室、坐标、协作网络），
> **没有任何患者诊疗数据**。如果我顺着"我这个症状该去哪家医院"给出推荐，那是在用不存在的数据回答不该我回答的问题——
> 答辩时一定被问倒。
>
> 所以系统做了双层判定：**129 个病征 / 就诊诉求词**命中即拒答；再加一层叙述特征兜底
> （"人群词 × 病程词"且全文没有任何机构筛选词，覆盖词表没收录的新写法）。拒答时**不产生任何结果行**，
> 并引导用户改成机构条件描述或转 AI 问诊导诊。
>
> 这样一来定位反而更清楚：系统做的是**医疗资源数据的查询与筛选**；AI 的两类职责都有硬边界——筛选链路里只把中文翻译成条件，问答三模式只基于当前真实筛选结果给建议。系统不做诊断、不给用药意见，也不产生任何清单外的机构名与统计数字。

**Q9.2：你说接了大模型，那现场断网怎么办？模型限流了怎么办？**（这题最容易被追问，答好了很加分）
> 我做了三层防护。**第一层，大模型不是主路径**：规则引擎和本地知识库能独立完成 95% 以上的提问，断网照常演示，只是长尾口语会提示"未匹配"。**第二层，结果三级缓存**：内存 → MySQL `dim_ai_cache` → 接口，重复提问实测从 3.6 秒降到 0.05 秒，重启服务依然有效。**第三层，额度适配**：Agnes 免费额度实测约 1 次/30~40 秒，连续提问会 429，所以我不做长时间的盲目重试（会让界面干等），而是快速失败并明确返回「免费额度限流，本地知识库不受影响」；同时提供 `etl/warm_ai_cache.py` 预热脚本，**答辩前把演示问法跑一遍写进缓存，现场零等待**。

**Q9.3：大模型怎么会返回一个医院表里根本不存在的科室？**（体现你想到了工程细节）
> 会。比如它可能返回"神经外科"，但我库里 29 个科室中没有这个科，join 之后就是 0 家医院，用户会以为系统坏了。所以我把**候选约束做了双重保险**：一是提示词里把 `dwd_dept_relation_clean` 里**真实存在的科室清单**动态取出来塞进去；二是拿返回值再和这份白名单做一次过滤，非清单内的直接丢弃。这样模型只可能"少答"，不可能"错答"。

**Q10：系统的创新点是什么？**
> 三点：① 用**协作网络归属**（儿科医联体/卒中中心/危重新生儿/危重孕产妇）度量"资源整合程度"，而非传统的单体规模指标；② 多源异构数据的**可验证整合方法**（别名映射 + 同名多院区消歧 + 官方名单交叉验证）；③ **离线单文件大屏**交付形态，零依赖可演示。

**Q11：协作网络匹配时遇到什么困难？**
> 主表同名多 ID（儿童医院 3 条、友谊 3 条、协和 3 条），需要排除体检部/分院/社区等次院区。解法是"名称规范化 + 精确匹配 + 前后缀包含 + 17 个手动别名"四级策略。私立机构"首儿窦店"不在主表内，如实跳过不强匹配。

**Q12：系统性能如何？**
> 9,678 行规模下查询为毫秒级；建索引后 EXPLAIN 扫描行数从 9,777 降到 33。大屏图表为前端聚合，首屏加载后无网络请求。

**Q13：如何部署？**
> `docker-compose.yml` 编排 spark-master / spark-worker / hospital-mysql 三容器（本机 MySQL 端口映射到 3307 避开占用）。Flask 可容器化或本机运行。演示场景直接用离线大屏，零部署。

**Q14：系统的不足？**
> ① 专科数据：2024 年西医临床重点专科名单官方未公示，维持"待公示"；② 坐标精度 55.7% 仅到区县级；③ 运营指标（门急诊量、执业医师数）不公开，无法获取；④ 协作网络目前只覆盖市级救治中心，区级待扩展。

**Q15：如果继续做，你会改进什么？**
> ① 引入真实用户行为数据做学习排序；② 补充实时数据更新管道（目前是离线批处理）；③ 扩展区级救治中心与综合医联体（依赖官方发布全市统一名单）；④ 增加移动端适配。

**Q16：这个项目你个人贡献了多少？**
> 独立完成：数据采集与治理、ETL 开发、数仓设计、前后端开发、数据核实、部署与文档。选题方向、技术路线与系统功能均由本人独立确定，指导教师负责阶段检查与论文写作规范的把关。
