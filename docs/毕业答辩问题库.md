> 用法：括号内为**代码位置/命令**，答辩被追问时可直接翻给对方看。
> 口径与《项目最终整改报告》《项目说明书》完全一致，数字以当前数据库实测为准（2026-09-20）。

## 〇、如果只准备三个问题

| 问题 | 标准答法 |
|---|---|
| **这个系统做什么？** | 整合北京 **9,789 家**医疗机构的公开资源数据，支持用**一句话**或**条件组合**做多维筛选、维度统计、机构对比与地图分布分析。 |
| **大数据体现在哪？** | 治理后数据入 **HDFS**（ODS 原始层）→ **Spark** 分层清洗（DWD）与五个维度汇总（DWS，Parquet 存 HDFS）→ 仅 ADS 服务层结果落 **MySQL** 供查询。作业按维度拆成独立模块，可 `--only` / `--from` 重跑。 |
| **为什么不做智能推荐？** | 课题本身是"资源整合 + 多维筛选"。而且系统**没有患者诊疗数据**，做就医建议就是拿没有的数据回答不该回答的问题——所以病征类输入一律硬拒答。 |

## 一、选题与定位

**Q1. 为什么选这个题目？解决什么问题？**
北京医疗机构信息分散在市卫健委、各区卫健委、医保局、政务数据网等多个公开渠道，格式不一、名称重复、类型口径混乱。
本系统做的是**整合 + 筛选**：把多源数据治理成一份可信的机构资源表，再让用户按区域、等级、类型、所有制、科室、协作网络、距离等维度自由筛选与统计。
（治理：`etl/govern_master.py`；筛选：`web/nlq.py` + `web/app.py`）

**Q2. 这和"医院推荐系统"有什么区别？**
推荐系统要回答"我该去哪家医院"，需要诊疗数据、医生数据、号源数据——本项目**都没有**，也不打算编造。
本系统回答的是"**符合我条件的机构有哪些、分布如何**"，数据边界与问题边界是对齐的。这是本轮整改最关键的一次定位收敛：
原先把主线做成了"输入症状 → 推荐医院"，现已下线，改为自然语言智能筛选（详见《项目最终整改报告》）。

**Q3. "多维筛选"体现在哪几维？**
七维：① 关键词 ② 行政区（16 区）③ 医院等级 ④ 机构类型 ⑤ 科室 ⑥ 协作网络 ⑦ 距离（Haversine，需设基准点）。
（`web/nlq.py` 的 `DISTRICTS` / `LEVELS` / `CATEGORIES` / `OWNERSHIP_ALIAS` / `SOURCE_RULES`；`web/app.py` 的 `/api/meta/filters`）

**Q4. 系统的目标用户是谁？**
三类：① **公众**——想按条件找机构的普通用户；② **研究者/学生**——需要北京医疗资源分布数据做分析；③ **管理者**——看区域资源结构、协作网络覆盖、数据治理质量。
所以除了筛选主线，还保留了「资源画像」「数据治理」两个查阅支撑页。

## 二、数据

**Q5. 数据从哪来？多少个文件？**
公开渠道多源文件：市/区医保局定点机构名单、社区卫生服务机构名录、各区卫健委名录与专题公开数据、重点专科公示名单、协作网络名单（儿科医联体/卒中中心/危重新生儿/危重孕产妇）、政务数据资源网、高德地理编码。
去重后 **70 个源文件** → 原始 13,803 条记录 → 去重合并 **9,789 家**机构。
（`data/processed/data_quality_report.md`；入湖脚本 `etl/upload_to_hdfs.py`）

**Q6. 9,789 家怎么去重的？**
按机构名称归一化（去括号后缀、全半角统一、更名与别名映射）分组，同名合并并保留来源计数 `src_count_int`。
最多的一家机构来自 **9 个**源文件。重名组 3,139 组。
（`etl/govern_master.py`；快照字段 `src_count_int` / `source_files` 可核查）

**Q7. 公立/民营怎么判定？**
**多源证据口径**：以经济类型字段为主，结合"国有 + 集体全资"归属判定，冲突时以权威来源（卫健委/医保局）优先。
结果：公立 **3,085** / 民营 **5,323** / 未标注 **1,381**。
（`ads_inst_search.ownership` / `ownership_src`，可回溯每家的判定来源）

**Q8. 医院等级怎么来的？有没有编？**
来自卫健委公示与机构名录；缺失的**不硬填**。
等级分布：三级 **213** / 二级 **212** / 一级 **833** / 未定级 **31**。
另有大量机构不属于医院分级评审范围（诊所、村卫生室、门诊部、社区卫生服务站等），单列为「**不适用医院分级**」，
避免出现"87% 未定级"这种假性结论（`ads_level_overview` 已按此口径剔除）。
（核实过程见 `docs/数据联网核实报告.md`）

**Q9. 坐标怎么补齐的？覆盖率多少？**
用高德地理编码（`/api/geocode` 代理 + `dim_poi_cache` 缓存）补全，坐标覆盖 **9,787 / 9,789 = 99.98%**。
未命中坐标的机构在距离排序中不参与距离计算，距离文案降级为「距市中心」。
（`etl/geocode_*.py`；前端 `resolveBase` 五级降级解析）

**Q10. 数据有哪些做不到的地方？**
如实披露三类边界：① 联系电话仅 5.8% 机构有公开号码；② 床位数公开率极低（已下线该字段）；
③ 部分区级名录的机构类型口径不一致，已按统一规则归一但在质量页标注。
（`docs/项目说明书.md` §5.4；前端数据质量页同步展示）

**Q11. 机构类型为什么是 10 类？**
这是本轮修复的一个**真实数据缺陷**：原先 DWD 归一化只覆盖到"体检中心"，导致 3,463 家基层机构
（社区卫生服务中心 299 / 社区卫生服务站 1,205 / 村卫生室 1,959）被错误并入"其他机构"。
补齐 3 个归一化分支后 `dws_inst_by_category` 由 7 行变 **10 行**。
（`spark/jobs/layer_dwd.py` 的 `category_norm`）

## 三、大数据链路

**Q12. 为什么用 HDFS？数据不放 MySQL 就行吗？**
职责不同：**HDFS 承载数仓**（ODS/DWD/DWS 以 Parquet 存，列式、可分区、适合批量分析），
**MySQL 只承载服务层**（ADS 结果表，供 Flask 做点查与筛选）。
把 13,803 条原始记录的分析过程放进 MySQL，等于用交易型数据库做分析型工作负载，是选型错误。
（`spark/jobs/common.py` 的路径常量；`docker-compose.yml` 5 容器）

**Q13. HDFS 里到底有什么？**
`/hospital/{ods/raw, ods/parquet, dwd, dws/{space,category,dept,network,time}, meta/snapshots}`，
自检实测 **21 个表/目录**可读（`dwd_institution_clean` 9,789 行 / `dwd_dept_relation_clean` 16,251 行 /
`dws_district_distance` 256 行 …）。
（`bash spark/run_all.sh --only deps` 或 `spark/jobs/check_deps.py`）

**Q14. 为什么 Spark 用单机模式？不是有集群吗？**
答辩要求明确要求"单机 Spark 依赖（Maven）"。默认 `SPARK_MASTER=local[*]`，
但**同一份代码、同一份 Maven 坐标**，改一个环境变量即可切 Standalone：
`SPARK_MASTER=spark://spark-master:7077 bash spark/run_all.sh`。
（`spark/run_all.sh` 第 25 行；`spark/jobs/check_deps.py` 两种模式都能识别）

**Q15. 为什么没有 Hive？**
Hive 的职责（SQL 元数据 + 计算引擎）已被 Spark SQL 全覆盖，引入会让依赖更重、与 Spark 元数据重复，
对本项目的数据规模没有收益。这是**有依据的取舍**，不是没做。
（`docs/项目说明书.md` §3.1 选型论证）

**Q16. 作业为什么要按维度拆？**
单脚本 407 行无法维护，也无法只重跑某一维。拆成 `layer_ods` / `layer_dwd` / `dim_space` / `dim_category` /
`dim_dept` / `dim_network` / `dim_time` / `layer_ads` / `run_all` 后，可以 `--only ads` 只落库、`--from dwd` 从明细层重跑。
（`spark/jobs/`；`run_all.py` 的 `STAGES` 定义）

**Q17. Maven 依赖怎么管的？**
用 `--packages com.mysql:mysql-connector-j:8.4.0` 由 Ivy 解析（含传递依赖），
并另交付 `spark/pom.xml` 作为依赖清单声明。缓存目录 `spark/.ivy2` 已 gitignore，**答辩现场无网也能复用**。
（`spark/run_all.sh` 第 23-24 行）

**Q18. 跑一次全链路多久？**
单机模式约 **135 秒 / 10 阶段**（ODS 15.8 / DWD 6.4 / 空间 7.2 / 类型 5.5 / 科室 6.6 / 网络 4.6 / 时间 9.5 / ADS 9.4 + 自检）。
本轮验证「时间维度 + ADS」增量重跑实测 **31.5 秒**。

**Q19. 数据仓库怎么分层的？**
ODS（原始入湖）→ DWD（清洗、去重、办别判定、类型归一、坐标关联）→ DWS（**五个维度**汇总：空间/类型等级/科室/协作网络/时间）
→ ADS（服务层宽表与概览）。ODS/DWD/DWS 全部 Parquet 存 HDFS，**只有 ADS 落 MySQL**。

**Q20. 索引做了什么优化？**
`ads_inst_search` 等表建 **26 个索引**，含协作网络四列联合索引。
坑：Spark JDBC 建表把字符串列建成 TEXT，MySQL 不允许 TEXT 直接建索引（错误 1170），必须用**前缀索引**（UTF-8 汉字 3 字节）。
实测典型多维筛选 `EXPLAIN rows` 由 9,777 → **33**。
（`etl/create_indexes.py`）

**Q21. 为什么每次重跑数仓后必须重跑索引脚本？**
因为落库用 `mode="overwrite"`（DROP + CREATE），**表被重建，索引全丢**。这是踩过的真实坑，已写进一键脚本固定顺序。
（`scripts/run_pipeline.sh` 第 3、4 步）

## 四、自然语言智能筛选（本轮主线）

**Q22. 一句话怎么变成筛选条件？**
规则引擎 `web/nlq.py` 五步：① 全角转半角、去噪 ② 词表扫描（行政区/等级/类型/所有制/来源/科室别名/SORT/统计意图）
③ 剩余片段做关键词，并剥离停用词（169 条）④ 意图判定（**统计 / 筛选 / 拒答**）⑤ 编译为参数化 SQL。
例：「朝阳和海淀的三级医院，按距离从近到远」→ 条件卡（行政区=朝阳区+海淀区 / 等级=三级 / 类型=医院）+ 排序=距离。

**Q23. 为什么不用大模型做主解析？**
三个理由：① **可复现**——同一句话任何时间、任何机器结果一致，答辩能当场验证；② **零成本零依赖**——断网可用；
③ **可解释**——命中的是词表条目，能说清"为什么解析出这个条件"。
大模型只在规则零命中时兜底，且提示词写死"只输出条件，不许输出机构名与数字"。
（`web/nlq.py` 顶部设计注释；`/api/nlq/ask`）

**Q24. 大模型会不会胡说八道？**
从设计上堵死：① 主路径不经过大模型；② 大模型输出只允许是条件字段，机构名与数字一律由 SQL 查询产生；
③ 三级降级（Agnes → 结果缓存 `dim_ai_cache` → 本地模板），失败绝不空白；④ 前端明确标注"所有数字来自数据库真实查询"。
（`web/nlq.py` 的 `AI_SCOPE_NOTE`；`web/app.py` 的 AI 设计要点注释）

**Q25. 用户问"我发烧了去哪个医院"会怎样？**
**硬拒答**。129 个病征/就诊诉求词 + 叙述特征兜底（人群词 14 个 × 病程词 21 个）双判定，
命中即返回固定文案（"不提供疾病诊断、用药建议或治疗推荐……"）并**不产生任何结果行**。
单文件形态同样拒答，双端文案逐字一致（`etl/verify_offline_nlq.py` 有断言）。
（`web/nlq.py` 的 `MEDICAL_WORDS` / `MEDICAL_REFUSAL`）

**Q26. 条件匹配度是什么？怎么算？**
`match = Σ(命中条件权重) ÷ Σ(本次条件权重之和)`，权重：行政区 0.30 / 等级 0.25 / 类型 0.20 / 所有制 0.15 / 来源 0.10。
**它只衡量"与本次条件的吻合程度"，不是医院实力评分**。这条区分要在答辩时说清楚，避免被理解成推荐算法。
（`web/nlq.py` 的 `MATCH_WEIGHTS` / `MATCH_FORMULA`；前端在排序说明里同步标注）

**Q27. 有哪些排序？**
5 种：**条件匹配度 / 距离 / 医院等级 / 科室收录量 / 机构名称**。双端（在线与单文件）完全一致——
为此专门给后端 `ads_inst_search` 补了 `sort=name`（原先只有前端本地排序有）。
（`web/nlq.py` 的 `ORDER_BY`；`web/app.py` /api/institutions 的 sort 参数）

**Q28. 两套前端的结果会不会不一致？**
不会。词表只有一份真源（`web/nlq.py`），由 `etl/export_nlq_lexicon.py` 导出并内联进单文件产物，禁止手抄。
`etl/verify_offline_nlq.py` 用 **349 项断言**逐字段比对解析、筛选、统计三层结果，目前全绿。
（踩过的坑：曾因参考实现用了旧字段名导致 3 项不一致，已修正为与前端同源字段）

**Q29. 说"按行政区统计"会发生什么？**
意图识别为「统计」，切换结果链：不再返回机构清单，而是按该维度分组汇总——图表（ECharts 柱图/饼图）+ 四列 KPI
（机构总数 / 覆盖分组数 / 最多的一组 / 最少的一组）+ 文字结论，并明确提示"按 XX 维度汇总，不是机构列表"。
支持 5 个维度：行政区 / 等级 / 类型 / 所有制 / 协作网络。

**Q30. 解析错了能改吗？**
能。解析结果是**可增删的条件卡**，用户点 × 即可去掉某条条件并重新查询；侧栏还有会话留痕，可一键回放上次的问法。

## 五、前端与可视化

**Q31. 为什么做两套前端？**
定位不同：**在线形态**（Vue 3 + Flask，`/spa/`）负责交互与实时查询；**单文件形态**（零依赖 `dashboard_offline.html`，8.77 MB）
内联数据快照与 ECharts，**断网、双击、GitHub Pages 都能演示**——答辩现场网络不可控，这是刚需。
两者共用同一套口径，不是"两套系统"。

**Q32. Vue 工程的技术栈与结构？**
Vue 3.5 + Vite 6 + Pinia 2 + Vue Router 4（hash 路由）+ ECharts 5.5 + axios。
`src/api.js` 是唯一 HTTP 通道，`src/store.js` 是唯一数据仓库（**页面组件不自行请求数据**），
`src/router.js` 用 hash 模式（产物挂在 `/spa/` 子路径，无需服务端 history 回退）。
（构建：`bash web/vue/build.sh`）

**Q33. ECharts 有什么坑？**
三个，都是真踩过的：① canvas 读不到 CSS 变量 → 必须从计算样式解析出**实色**再喂给 ECharts，换主题要重新解析并重绘；
② `formatter` 传**函数**时不做 `{b}/{c}` 模板替换，会原样印出 `{b}`，必须自己拼字符串；
③ 容器必须有**显式高度**，否则高度为 0 直接白屏。
（`web/vue/src/charts.js` 的 `tokens()`；`web/app.js` 的 `loadTokens()`）

**Q34. 地图怎么做的？**
北京 16 区 GeoJSON 边界（`web/vendor/beijing_geo.json`，Vue 侧由构建脚本同步到 `web/vue/geo/`）
+ `effectScatter` 撒点 9,789 个，列表行悬停 ↔ 地图点位**双向互指**（`SCATTER_IDX` + `ROW_EL_BY_ID` + `dispatchAction`，带去抖）。
点击点位打开机构详情抽屉。

**Q35. 主题切换怎么保证图表不花？**
令牌分层（`<html data-theme>` 只换 CSS 变量），默认 dark，白天主色加深。切换后必须**重新解析颜色 + 重绘所有图表 + 重画地图**，
`applyTheme()` 与 `drawMap()` 都可重入。

## 六、工程与部署

**Q36. 怎么从零复现整个系统？**
一键脚本：`bash scripts/run_pipeline.sh`（起容器 → 数据入湖 → Spark 全链路 → 建索引 → 构建前端 → 校验）。
分步版（8 步）见 `docs/项目说明书.md` §8.2。
（`--skip-ingest` / `--skip-front` / `--skip-verify` / `--from` / `--only` 可选）

**Q37. Docker 为什么有 5 个容器？**
hdfs-namenode(9870) + hdfs-datanode + spark-master(8080) + spark-worker + hospital-mysql(3307)。
HDFS 镜像是在 `docker/hadoop/` **自建**的（官方 `apache/hadoop:3.3.6` 只有 amd64，M1 上 QEMU 起不来）。

**Q38. 怎么保证代码改完没坏？**
五道校验：`verify_artifacts.py`（产物完整性）、`verify_offline_nlq.py`（双端一致性 349 项）、
`smoke_dashboard.py` / `smoke_nlq_ui.py`（单文件形态）、`smoke_vue.py`（Vue 端到端）、
`verify_layout.py`（响应式版面，5 档宽度 × 4 页面 68 项）。
本轮整改后全部通过、运行时错误 0。

**Q39. 遇到过最难的坑？**
① **HDFS 镜像**：官方只有 amd64，buildkit 拉基础镜像 401，必须先 `docker pull` 再 `DOCKER_BUILDKIT=0` 构建；
② **Spark 容器写 HDFS 权限**：进程 uid=185，需 `HADOOP_USER_NAME=root` 且保留 HDFS 权限校验；
③ **headless Chrome 跑真库版会挂**：ECharts 持续动画让虚拟时间不收敛，验证时必须换成空桩 ECharts；
④ **空桩不能按体积取最大 script 块**：离线大屏里数据快照（6.6 MB）比 ECharts（1.0 MB）还大，按体积挑会把数据删掉，
页面不报错但列表全空——必须按内容标记定位。
⑤ **Spark 容器时区是 UTC**：批次日期会偏差一天，已固定 `spark.sql.session.timeZone=Asia/Shanghai`。

**Q40. 如果重做会怎么改？**

**Q41. 科室数为什么大多数医院都不显示数字？**

因为那一列**大多数值不是实测的**。`dept_count` 取自 `data/processed/hospital_depts.csv` 的行数，
而该表 `source` 有四类：`rule`（按「机构等级 × 类型」套通用清单，三级 19 / 二级 13 / 一级 6~7）
11,840 行、`name`（按机构名推断，如「中医医院」→ 中医内科、针灸推拿科）3,900 行，
两者合计占 **96.8%** 是推导；真实的只有 `key_depts` 488 行 + `specialty` 23 行。
逐家核对后，真正具备**在线核实**来源（机构官网 / 百科词条明确写明「共设 N 个临床、医技科室」）
的只有 **34 家**——所以定版口径是「**无据不显数字**」：只有这 34 家在列表与详情显示具体科室数，
其余 9,755 家一律显示「**科室资料待补全**」，悬停说明原因。
推导出的科室名仍参与科室维度的检索与排序，但不作为事实对外展示——
这是「宁缺勿伪」原则在字段级的一次落实，和床位字段下线是同一套逻辑。

（过程中还修掉一个具体 bug：21 家首医系医院的百科词条共用同一段模板文字
「开放编制床位2500张；共设59个临床、医技科室」，抓取时被当成各家自己的科室数。
判据已改为「同一段证据被 ≥3 家不同机构共用 → 整条作废」，且只认数字紧邻上下文的科室总数声明。）

（`web/app.js` 的 `deptLabel()`；`web/vue/src/deptLabel.js`；`etl/build_deptcount_online.py`；`etl/smoke_nlq_ui.py` 的 J 段断言）
