## 一、项目概述

### 1.1 背景

北京市医疗机构信息公开程度较高，但分散在市医保局、各区卫健委、各类专科公示名单等**70 个异构数据文件**中，格式、字段、命名口径各不相同（CSV/GBK/伪装成 CSV 的 xlsx/老 xls 混杂）。普通用户想要回答"我家附近哪家医院有儿科、而且是三级、并且属于儿科医联体"，需要同时打开十几个网页逐条比对。

本项目要解决的不是"再做一个漂亮的大屏"，而是**先把 70 份文件真正整合成一份可信的数据资产，再在这份资产上提供多维筛选与可视化**。

### 1.2 目标

| 目标 | 度量 |
|---|---|
| 数据整合 | 70 个源文件 → 1 份主表（9,678 家机构 × 42 列），机构名+区县级别去重 |
| 数据可信 | 坐标覆盖 99.97%；办别未标注 1,410 家（14.6%）；等级适用范围可解释 |
| 大数据链路真实 | 数据从 HDFS 读、预处理结果回写 HDFS、分析结果落 MySQL，全链路可一键重跑 |
| 多维筛选 | 7 个维度（关键词/区域/等级/类型/科室/协作网络/距离）任意组合 + 4 种排序 |
| 可视化 | 7 个视图、16 区地图撒点、图表与列表联动互指 |

### 1.3 成果清单

| 类别 | 成果 |
|---|---|
| 数据资产 | `data/processed/master_institutions.csv`（9,678 × 42）及衍生数据表 |
| 数据治理代码 | `etl/` 66 个 Python 脚本（治理管线 / 地理编码 / 词表导出 / 校验与冒烟） |
| 数仓代码 | `spark/jobs/` 13 个模块，共 1,682 行 |
| 服务端 | `web/app.py` 1,562 行，25 个 API 接口（另加首页与 `/spa/` 静态托管，共 28 个路由） |
| 筛选引擎 | `web/nlq.py` 834 行（词表 + 条件解析 + 参数化 SQL + 维度统计）——**全系统唯一口径真源** |
| 前端（在线） | `web/vue/`（Vue 3 工程：9 视图 + 6 组件 + api/store/charts），构建产物由 Flask 挂载在 `/spa/` |
| 前端（单文件） | `web/dashboard.html` + `web/app.js`（2,658 行）+ `app.nlq.js` / `app.nlq.ui.js`（离线筛选引擎与界面层），派生出 3 份可交付 HTML |
| 部署 | `docker-compose.yml` 5 容器（HDFS ×2 / Spark ×2 / MySQL ×1）；全链路一键脚本 `scripts/run_pipeline.sh` |
| 文档 | 本说明书、《项目最终整改报告》《毕业答辩问题库》《功能点-代码对应表》《系统运行流程》《毕业论文》《答辩与简历讲解手册》等 12 份 |

| F11 | 地址定位与距离计算 | `/api/geocode`、`resolveBase`、`haversine` |

### 2.2 非功能需求

- **离线可用**：`dashboard_offline.html` 双击即开，零依赖、零网络请求（演示抗风险）。
- **可重跑**：从入库到落库全链路一键重跑，无需手工补数据。
- **可验证**：提供三条自检命令，现场即可证明链路真实（见第九章）。
- **不伪造**：任何指标都能对应到具体代码与数据行；数据缺失如实标注，不补零、不臆造。

### 2.3 范围边界（明确不做的部分）

- **不做实时数据**：数据为公开静态名录，快照日期即数据截止日，不做实时同步。
- **不做医疗建议**：病征类输入一律硬拒答，不推荐科室、不推荐医院、不给诊断或用药意见。
- **不做无依据的推荐**：系统是"资源整合 + 多维筛选 + 排序"，不构建用户画像、不做个性化推荐算法；排序中的「条件匹配度」只衡量与本次筛选条件的吻合度。

## 三、技术选型与论证

### 3.1 选型总表

| 层 | 选型 | 版本 | 选择理由 |
|---|---|---|---|
| 分布式存储 | HDFS | 3.3.6 | 承载 ODS/DWD/DWS 分层数据，练习真实大数据存储；本题数据量虽小，但链路要真 |
| 计算引擎 | Apache Spark (PySpark + Spark SQL) | 3.5.3 | 列式读写 + 分层建模 + 多维度聚合，是数仓作业的主力 |
| 业务数据库 | MySQL | 8.0 | 只存 ADS 服务层结果，供 Flask 快速查询 |
| 依赖管理 | Maven 坐标（`spark-submit --packages`） | — | 依赖可声明、可复现，替代早期手工 `--jars` 挂包 |
| 容器化 | Docker Compose | — | 5 容器一键拉起；**HDFS 镜像为自建 arm64**（官方仅 amd64，Mac M1 跑不了） |
| 服务端 | Flask + PyMySQL | — | 轻量 REST 服务，22 个接口，与前端完全解耦 |
| 前端（在线） | **Vue 3 + Vite + Pinia + Vue Router** | Vue 3.5 / Vite 6 | 前后端分离的标准工程形态，通过 `/api/*` 取数 |
| 前端（单文件） | 原生 JS SPA + ECharts | 5.5.1 | 零依赖单文件，双击即开，主线 + 查阅都能跑；见 3.5 |
| 数据抓取/治理 | Playwright + pandas | — | 百科词条需真实浏览器渲染（curl 直接 403） |

### 3.2 为什么「HDFS 存数仓 + MySQL 存服务层」而不是二选一

这是本项目架构上最关键的一个决定：

- **HDFS 存 ODS/DWD/DWS**：这三层是"数据加工过程"的产物，体量大、需要列式压缩与批量扫描，且要求可回溯（ODS 保留原始形态）。放 HDFS 是数仓的标准做法。
- **MySQL 只存 ADS**：服务层要支撑 Flask 的高频点查（按 id 取详情、按条件分页筛选），需要索引与低延迟。把 6MB 的明细表塞进 MySQL 反而拖慢一切。

一句话：**HDFS 负责"算得动"，MySQL 负责"查得快"**，两者职责不重叠。

### 3.3 为什么把作业按维度拆分

早期的实现是一个 407 行的单体 ETL 脚本 `spark/etl_hospital.py`，问题很明显：改一个维度的逻辑要通读全文，跑错一个环节要全量重来，代码里也看不出"分析了哪几个维度"。

现在拆成 `layer_ods / layer_dwd / dim_space / dim_category / dim_dept / dim_network / dim_time / layer_ads`，由 `run_all.py` 的 `STAGES` 表统一编排，可以 `--only deps` 只跑自检、`--from space` 从空间维度续跑。**维度即模块**，这与"按维度组织代码"的要求直接对应。

### 3.4 为什么用 Maven 坐标管理依赖

作业运行需要 MySQL JDBC 驱动。早期做法是手工下载 jar 再用 `--jars` 挂载 —— 换台机器就要重新找包，版本也说不清。

现在统一为在 `spark/pom.xml` 里声明坐标，运行时由 `spark-submit --packages com.mysql:mysql-connector-j:8.4.0` 交给 Ivy 解析，并缓存到挂载目录 `spark/.ivy2`，**答辩现场无网也能复用**。`pom.xml` 同时是依赖矩阵的权威声明，可直接用于论文附录。

### 3.5 前端为什么是「双形态」：Vue 工程 + 零依赖单文件

要求⑥是"Vue + Flask 前后端分离"。本项目**已按此落地**，同时刻意保留了原有的单文件形态，
两者并存、共用同一套后端接口与同一套筛选口径：

| 形态 | 入口 | 取数方式 | 定位 |
|---|---|---|---|
| **Vue 在线形态** | `http://localhost:5001/spa/` | `GET /api/*` → Flask → MySQL | 标准前后端分离工程，源码在 `web/vue/`；数据可实时更新、会话留痕、AI 兜底可用 |
| **单文件形态** | `dashboard_offline.html` 或 `/` | 内联快照 `window.__SNAPSHOT__` + 内联词表 `window.__NLQ_LEX__` | 零依赖、双击即开、可直接分享链接；**查阅与智能筛选两种能力都具备** |

**单文件形态为什么也能筛选**（2026-09-20 整改后的能力）：

早先单文件形态只内联了机构快照，只能查阅；主线入口是一个指向在线形态的硬链接
`href="/spa/"`——在本地 `file://` 下被拦截提示，在静态托管（GitHub Pages）上是**直接 404**。
现在把主线的**解析与查询搬到了前端**：

- 词表由 `etl/export_nlq_lexicon.py` 从 `web/nlq.py` 导出为 `web/nlq_lexicon.json`（10.1 KB）
  并在构建时内联，**不手抄**——这是"两套前端不是两个系统"的前提；
- `web/app.nlq.js` 用同一套规则解析中文条件，并在内联快照上做筛选、排序与维度统计；
- `web/app.nlq.ui.js` 提供双通道输入、条件卡、KPI、清单、地图与统计图表；
- 病征类输入在单文件形态下**同样硬拒答**，文案与后端逐字一致。

两种形态的结果由 `etl/verify_offline_nlq.py` 用 **351 项断言**逐字段比对（解析 22 条问句、
筛选 10 组条件、统计层输出），**保证不是两个系统**。

**Vue 工程的技术要点**（`web/vue/`，9 视图 / 6 组件 / 1 数据仓库）：

- `src/router.js` 用**哈希路由**：产物挂在 `/spa/` 子路径，哈希模式不需要服务端 history 回退，
  构建产物直接双击也能跑，兼顾了兜底能力。
- `src/store.js`（Pinia）是**唯一数据仓库**：查询条件、分页、距离基准点、对比选择、主题状态
  集中管理，页面组件不自行请求数据，保证"条件一变、全站同步"。
- `src/api.js` 是**唯一 HTTP 通道**，统一拦截响应与错误；前端不直连数据库、不读快照文件。
- `src/charts.js` 解决本项目最容易翻车的一点：**ECharts 画在 canvas 上，读不到 CSS 变量**。
  所有图表配色必须经 `tokens()` 把 `var(--x)` 解析成实色再喂给 `setOption`；主题切换后
  必须重新解析并重绘，否则暗色主题下仍会显示亮色配色。

**为什么不直接删掉单文件形态**：`dashboard_offline.html` 是一个 8.3 MB 的自包含文件，
双击即开、不依赖 Python/Docker/数据库/网络，在答辩现场、简历投递、发给别人看这三种场景下极其可靠
（GitHub Pages 上可直接访问）。Vue 形态证明工程能力，单文件形态保证"**一定能演示、且一定能分享**"，
两者不是替代关系，而是"在线标准形态 + 零依赖分发形态"。

> 源码组织：`web/vue/src/views/` 七个视图一一对应侧栏导航项，
> `components/` 放 SideNav / TopBar / FilterBar / InstTable / DetailDrawer / CompareDialog。
> 构建：`bash web/vue/build.sh` → 产物 `web/vue/dist/`（已入库，Flask 挂在 `/spa/`）。

## 四、系统架构

### 4.1 七层架构

```
① 数据源层   data/ 70 个异构文件（医保局/区卫健委/专科名单）
                    │  清洗、合并、联网核实、地理编码
② 数据治理层 etl/*.py（56 个脚本）→ data/processed/*.csv
                    │  etl/upload_to_hdfs.py
③ 数据入湖层 HDFS /hospital/ods/raw（原始 CSV 落盘）
                    │  spark/jobs/layer_ods.py（列式化）
④ 计算层     HDFS /hospital/{ods/parquet, dwd, dws/{space,category,dept,network,time}}
                    │  spark/jobs/layer_ads.py
⑤ 存储层     MySQL hospital 库（20 张表，ADS 服务层）
                    │  web/app.py（25 个 API 接口）
⑥ 服务层     JSON API over HTTP（Flask，默认 5001，28 个路由）
                    │  axios → /api/*   │   或 内联快照 __SNAPSHOT__ + __NLQ_LEX__
⑦ 展现层     双形态，共用同一套数据与同一套筛选口径：
             · Vue 3 SPA（web/vue/，挂载 /spa/）            ← 前后端分离形态
             · 单文件（dashboard_offline.html，零依赖）      ← 本地解析与查询形态（主线 + 查阅都能跑）
```

### 4.2 部署拓扑（Docker Compose，5 容器）

| 容器 | 镜像 | 端口 | 作用 |
|---|---|---|---|
| `hdfs-namenode` | hospital-hdfs:3.3.6（**自建 arm64**） | 9870 / 8020 | HDFS 元数据与 RPC 入口 |
| `hdfs-datanode` | hospital-hdfs:3.3.6 | 9864 | HDFS 数据块存储 |
| `spark-master` | apache/spark:3.5.3 | 8080 / 7077 | Spark 提交入口；**默认单机模式下作业也在此容器内执行** |
| `spark-worker` | apache/spark:3.5.3 | 8081 | 可选：仅集群模式下参与计算 |
| `hospital-mysql` | mysql:8.0 | 3307→3306 | ADS 服务层业务库（宿主机 3306 被本地 MySQL 占用，故用 3307） |

> Spark 容器通过挂载 `docker/hadoop/conf/{core-site.xml,hdfs-site.xml}` 到 `/opt/spark/conf`（该目录在 Spark 默认 classpath 上）获得 HDFS 客户端能力；作业统一以 `hdfs://namenode:8020/hospital` 为根路径。

## 五、数据资源与治理

### 5.1 数据来源

| 来源 | 说明 | 规模 |
|---|---|---|
| 北京市医保局定点医疗机构名录 | 含机构名称、地址、等级 | 4,876 条 |
| 社区卫生服务机构名录 | 社区卫生服务中心 + 服务站 | 1,972 条 |
| 各区卫健委公开名录及专题数据 | 区级机构明细 | 6,955 条 |
| 重点专科公示名单 | 国家级 / 市级临床重点专科 | 43 条 |
| 百度百科（在线核实） | 办别、等级、科室数、重点科室 | 2,000+ 词条访问 |

原始记录合计 13,803 条，按「机构名标准化 + 区县」去重后 9,791 条，最终主表 9,678 条。

### 5.2 治理流程

1. **盘点**：`inventory_sources.py` 以子进程隔离方式解析每个文件，防单文件崩溃拖垮全盘。
2. **读取**：`read_tables.py` 自动识别真 CSV（utf-8/gb18030，逗号/分号/制表符）、xlsx（含伪装成 .csv 的）、老 .xls。
3. **清洗合并**：`clean_merge.py` 字段映射 + 机构名标准化 + 去重。
4. **治理**：`build_grade_scope.py` 派生等级适用范围（`grade_scope`，唯一真源）→ `merge_dup_institutions.py` 按「一证一行」收拢同名 / 多牌子记录（9,789 → 9,678）→ `build_alias_map.py` 把被折叠的挂牌名连同**执业编码证据**落盘为 `alias_map.csv`（**机构数不变**，见 5.4）。三者均幂等，已串进 `scripts/run_pipeline.sh` 第 0.5 步。
   > `govern_master.py` 是早期的治理合并脚本，已被上面三条取代：它会按固定字段白名单重写主表，**重跑会清掉后续挂上的派生列**（`national_specialty` / `net_*` / `ownership_online` / `dept_count_online`），因此不在流水线里。
5. **在线核实**：见 5.3。
6. **地理编码**：`geocode_amap.py` 调高德 Geocoding 批量补经纬度，带缓存与限速。
7. **入湖**：`upload_to_hdfs.py` 把治理结果与行为日志灌入 HDFS，逐个比对字节数与行数。

### 5.3 在线核实（本项目数据可信度的主要来源）

| 核实项 | 方法 | 结果 |
|---|---|---|
| **办别** | 百度百科信息栏（医院性质 > 经济类型 > 经营性质）+ 名称规则引擎（军队系 25 / 国企职工 14 / 高校附属 31 / 政府办社区 20 / 区属直称 13） | 公立 **2,979** / 民营 **5,289** / 未标注 **1,410**（未标注从 1,514 降至 1,410） |
| **医院等级** | 同上网抓取 + 逐条比对 | 修正 2 家；三级 180 / 二级 189 / 一级 480 / 未定级 25 / 不适用医院分级 8,804（2026-09-22 清除 335 家非参评机构被误盖的等级；同日经三路字段补全，非空由 922 增至 849，应参评口径补全率 **97.1%**） |
| **重点专科** | 权威名单（市卫健委 2018/2020 通知、2021/2022 疫情专项、2024/2025 单项 + 9 家头部医院官网）+ 212 家三级医院百科抓取 | 建立 `national_specialty` / `municipal_specialty` / `feature` 三级专科信号 |
| **科室数量** | 主源好大夫在线「N个科室」官方口径 + 百科「主要科室/科室设置」章节；仅取在线核实值，不用推导值 | **301 家**在线核实（好大夫 267 + 百科 34；301医院=165、同仁=67、中日友好=68、世纪坛=56、协和=37…），ADS 取值 `COALESCE(online, 源条目数)`；另有 **8,279 家（84.6%）** 基层机构（诊所/村卫生室/门诊部/社区卫生服务站/医务室/护理站）按各自《基本标准》以「诊疗科目」执业、**本就不设科室建制**，如实标注「**不设科室分科**」；其余才标「科室资料待补全」。展示档位按**类型优先**判定：显数字 **280 家**（301 家中有 21 家落在六类上，仍显"不设科室分科"）／不设科室分科 8,279／待补全 1,230——三档穷尽（=9,678），判据与「等级适用范围」同源 |
| **稀疏字段补全** | 源文件回收（离线遍历 70 份源文件）× 百科 infobox 复用（不新增请求）× 好大夫在线逐家核实（435 家），三路统一经 `etl/apply_field_patch.py` 回写主表；**只填空、不覆盖、冲突整条丢弃、不写占位值** | 电话 570 → **815**（8.4%）、等级 922 → **849**（应参评 874 家，补全率 **97.1%**）、等次 175 → **223**；冲突 29 条留档不改、越界 4 条被等级适用范围判据拦下；交通 17 / 官网 15 公开渠道确无系统出处，如实保留为空 |

**三个判定陷阱（已在代码中显式处理）**：
- 「主管部门 = 卫健委」**不等于**公立 —— 民营医院的监管单位同样登记卫健委，不能作为依据。
- 「医院性质 = 非公立」包含"公立"子串 —— 必须先判否定词再判关键词，否则会批量误判。

- **科室数被百科模板污染**：21 家首医系医院的词条简介是**同一段模板文字**「开放编制床位2500张；共设59个临床、医技科室」，抓取时被当成了各家自己的科室数。判据已改为「同一段证据被 ≥3 家**不同机构**共用即整条作废」（判不同前先做机构名归并），且只认**数字紧邻上下文**的科室总数声明——按整句关键词否决会误杀「设有80个科室，展开床位2763张」这类真实值。

### 5.4 数据边界（如实披露，不粉饰）

| 现象 | 真实原因 | 处理方式 |
|---|---|---|
| 1,410 家办别未标注 | 多为村卫生室、个体诊所，公开渠道确无办别信息 | 保留"未标注"，标注 `ownership_src` 来源，不强行推测 |
| 8,804 家"不适用医院分级" | 诊所/村卫生室/门诊部等本身不参加医院等级评审 | 派生 `grade_scope` 字段区分，避免"未定级占比虚高"的误读 |
| 353 家名称含「医院」的机构等级缺失 | 百科词条中确无等级字段 | **如实保留为数据边界**，不补零、不猜测 |
| 251 家村卫生室未标注办别 | 村办/私人办混合，无法单一归类 | 有意保留 |
| 11 个挂牌名不单独成条 | 它们与宿主机构**共用同一执业许可证**（同一医疗机构编码 / 医保定点编码），不是独立机构 | 按「一证一行」计数；映射连同编码证据落盘为 `data/processed/alias_map.csv`，逐条依据见 `govern_report_alias.md` |
| 按挂牌名（如「交道口社区卫生服务中心」）检索不到宿主行 | 检索只匹配 `name`，而挂牌名不进 `name`（见 5.2 第 4 步） | **如实记录为已知局限**，见 11.2；正确改法是让检索同时匹配别名表，而不是把牌子塞回机构名 |

> 答辩口径：**缺失是数据的真实边界，而不是解析漏损**；系统通过"来源标注列"让每一条数据的可信度都可追溯。

## 六、数仓设计

### 6.1 分层规范

| 层 | 存储 | 职责 | 是否清洗 |
|---|---|---|---|
| ODS | HDFS `/hospital/ods/parquet` | 原始数据列式化，schema 与源文件一致 | **不清洗**，保证可回溯 |
| DWD | HDFS `/hospital/dwd` | 清洗 + 标准化 + 坐标关联 + 在线核实结果合并 | 清洗 |
| DWS | HDFS `/hospital/dws/<维度>` | 按 5 个分析维度轻度汇总 | 聚合 |
| ADS | MySQL `hospital` 库 | 面向业务系统的服务层结果 | 服务化 |
| META | HDFS `/hospital/meta/snapshots` | 每次跑批追加一条批次快照 | — |

### 6.2 DWD 层清洗规则

1. 机构 `id` 纯数字防御 + 按 id 去重
2. 区名去掉"北京"前缀（"北京市朝阳区"→"朝阳区"）
3. `level_norm` 等级归一化（含 `grade_scope = not_applicable` → "不适用医院分级"）
4. `category_norm` 类型归一化
5. 关联 geocode 坐标缓存（按 id 去重，防 join 膨胀）+ 坐标精度分桶（high / rough / missing）
6. **`COALESCE(online, 原值)`**：在线核实结果优先于源值 —— ⚠️ 该合并必须置于 `level_norm` 派生**之前**，否则归一化会基于旧值计算

### 6.3 五个分析维度（DWS）

| 维度 | 模块 | 产出表 | 行数 |
|---|---|---|---|
| 空间 | `dim_space.py` | `dws_inst_by_district` / `dws_district_center` / `dws_district_distance` | 16 / 16 / 256 |
| 类型与等级 | `dim_category.py` | `dws_inst_by_level` / `_by_category` / `_by_ownership` | 5 / 7 / 3 |
| 科室 | `dim_dept.py` | `dws_dept_coverage` / `_by_district` / `_density` | 29 / 377 / 16 |
| 协作网络 | `dim_network.py` | `dws_network_summary` / `_members` | 4 / 157 |
| 时间 | `dim_time.py` | `dws_time_daily` / `_event` / `_feature` | 6 / 14 / 6 |

其中 `dws_district_distance` 是 **16×16 的 Haversine 球面距离矩阵**，是"空间可达性"分析与距离筛选的数据基础。

### 6.4 ADS 服务层（MySQL 20 张表）

| 类别 | 表 |
|---|---|
| 服务副本（Flask 直接查） | `dwd_institution_clean`、`dwd_dept_relation_clean`、`dwd_specialty_clean`、`dws_inst_by_district`、`dws_inst_by_level`、`dws_inst_by_category`、`dws_dept_coverage` |
| 应用宽表 | `ads_inst_search`（9,678 × 42，检索主表）、`ads_district_overview`、`ads_level_overview`、`ads_specialty_hospital` |
| 分析结果 | `ads_network_summary`、`ads_time_trend`、`ads_time_feature`、`ads_etl_snapshot`、`ads_dept_strength`（科室实力指数 16,729 条，**下线主线遗留：作业仍产出，当前无前端引用**） |
| 维度表 | `dim_disease_dept`（症状-科室字典 417 条，**历史遗留：旧导诊能力的底座，未参与筛选链路**）、`dim_poi_cache`（地理编码/周边缓存）、`dim_ai_cache`（大模型结果缓存） |
| 行为 | `fact_user_event`（埋点） |

> 2026-09-20 整改：旧主线「就医决策」下线，其留痕表 `user_plan` 已 DROP，全库 21 → **20 张**。

**索引**：`ads_inst_search` 建 5 个索引（含协作网络四列联合索引），全库共 26 个索引，由 `etl/create_indexes.py` 统一维护。

## 七、功能模块

### 7.1 信息架构：1 条任务主线 + 4 个查阅支撑页

系统的定位不是"把数据摊开给人看"，而是**帮人把一次机构筛选做完**。因此导航分两层：

| 层 | 入口 | 内容 |
|---|---|---|
| **主线** | **智能筛选** | 双通道：说一句话 → 条件卡 → 真实数据结果；或直接选条件（详见 7.2） |
| 查阅 | **找机构** | 子标签「机构列表 / 条件筛选」：七维筛选、分页列表（20/页）、行悬停 ↔ 地图互指、详情抽屉、机构对比 |
| 查阅 | **资源画像** | 子标签「总览 / 结构分析」：6 张 KPI 卡、北京 16 区地图撒点、类型构成、各区 TOP、等级分布、办别构成；分析图表随筛选联动重绘 |
| 查阅 | **数据治理** | 子标签「整合过程 / 质量核验」：多源整合流程与去重统计、字段完整率、坐标精度分布、数据边界披露 |
| 查阅 | **系统说明** | 数据来源、清洗流程、技术栈、口径说明 |

> 2026-09-19 重构：此前是 7 个平级视图。平级排布会让人以为"这就是个能切换图表的大屏"，主次不分；收敛成 4 个支撑页后，每个页面回答一个完整的问题，主线与查阅的关系一目了然。旧路径（`#/institutions` 等）已做重定向，深链接不失效。
>
> 2026-09-20 整改：主任务入口由「就医决策」改为「**智能筛选**」。原四步工作台（说需求 → 看候选 → 做比较 → 拿方案）连同其接口（`/api/plan`、`/api/triage`、`/api/plans`）、离线数据包与留痕表 `user_plan` 一并下线——"输入症状推荐医院"与本课题的"资源整合 + 多维筛选"不是同一件事，且系统没有患者诊疗数据。整改全过程见《项目最终整改报告》。

### 7.2 智能筛选（任务主线）

主线的产出物不是"一张就医方案"，而是**一份可核对的筛选结果**：条件是什么、命中多少家、分布在哪儿、按什么排的。

**两条通道，同一条结果链**：

| 通道 | 交互 | 系统做了什么 |
|---|---|---|
| **自然语言** | 输入"朝阳和海淀的三级医院，按距离从近到远" | `web/nlq.py` 解析 → 条件卡（行政区 / 等级 / 类型 / 排序）→ 参数化 SQL 查 `ads_inst_search` |
| **条件选择** | 直接选行政区 / 等级 / 类型 / 所有制 / 来源 / 科室 / 关键词 | 走同一条查询链路，结果结构完全一致 |
| **维度统计** | 说"按行政区统计""等级分布""类型构成""协作网络分布" | 意图切到统计：不再返回机构清单，而是分组汇总 + ECharts 图 + 四列 KPI + 文字结论 |

**结果区**：命中数 KPI（总数 / 三级 / 二级 / 公立）→ 分页清单（行悬停与地图点位双向互指）→ 地图撒点 → 数据来源与口径说明 → 会话留痕（可一键回放上次问法）。

**三条硬约束（答辩必答）**：

1. **规则优先**：解析主路径是词表 + 正则，完全离线、可复现、可解释；大模型只在规则零命中时兜底，且提示词写死"只输出条件，不许输出机构名与数字"。
2. **真实数据**：所有条件最终编译成**参数化 SQL** 打到 MySQL；机构名、数量、占比无一处来自模型生成。前端「数据来源与口径说明」把这一点直接展示给用户。
3. **边界拒答**：病征类输入**硬拒答**，不给任何结果行（判定规则见 7.4）。

**词表单一真源**：词表只有一份正本（`web/nlq.py`），由 `etl/export_nlq_lexicon.py` 导出为 `web/nlq_lexicon.json` 并内联进单文件产物，禁止手抄。实测导出口径：行政区 17 / 等级 4 / 机构类型 10 / 所有制 3 / 来源规则 4 / 科室别名 34。

**两种形态都具备这条主线**：

| 环节 | 在线形态 | 单文件形态 |
|---|---|---|
| 解析与查询 | Flask `/api/nlq/*` + MySQL | `web/app.nlq.js` 本地解析 + 内联快照查询（`file://` 下也能跑） |
| 词表 | `web/nlq.py` 常量 | 构建时导出的内联词表（同一份真源） |
| 维度统计 | `/api/statistics/<dim>`（5 个维度） | 本地按维度聚合 |
| 拒答 | 后端判定 | 前端同样判定（文案逐字一致） |
| 一致性保障 | — | `etl/verify_offline_nlq.py` **351 项断言**逐字段比对 |

### 7.3 七维筛选与排序

**筛选维度**：① 关键词 ② 区域（16 区）③ 等级 ④ 类型 ⑤ 科室 ⑥ 协作网络 ⑦ 距离（Haversine，需设基准点）

**排序（5 种，双端一致）**：

| 排序 | 说明 |
|---|---|
| 条件匹配度 | 默认排序，公式见 7.4；**只衡量与本次条件的吻合程度** |
| 距离 | 需设基准点；未设基准点时按市中心（天安门）计，文案降级为「距市中心」 |
| 医院等级 | 三级 → 二级 → 一级 → 未定级 |
| 科室收录量 | 按系统**已收录到的科室条目数**降序。该字段 80.3% 为推导值（`rule` 等级×类型模板 + `name` 机构名推断），**只反映收录深度，不代表机构规模**；只有 280 家在线核实机构在界面显数字 |
| 机构名称 | 按码位序（不用 `localeCompare`，保证前后端一致） |

> ⚠️ **口径勿混写**：历史材料中的"综合评分 = 等级 0.5 + 距离 0.3 + 科室 0.2"是**旧版默认排序**，现已被「条件匹配度」取代；
> 旧主线（就医决策）另有一套"专科实力 + 偏好加权"的打分，随该主线一并下线，材料中不应再作为现行口径出现。

### 7.4 关键算法

| 算法 | 位置 | 说明 |
|---|---|---|
| 中文条件解析 | `web/nlq.py`（834 行） | 全半角归一 → 词表扫描（34 条科室别名、18 条区名与常见错别字纠正）→ 停用词剥离（169 条）→ 意图判定（筛选 / 统计 / 拒答）→ 参数化 SQL 编译 |
| 医疗边界拒答 | `web/nlq.py` 的 `MEDICAL_WORDS`（129 词）+ `NARRATIVE_CROWD`(14) × `NARRATIVE_COURSE`(21) | 词表命中即拒答；"人群词 + 病程/不适词且全文无任何机构筛选词"作为兜底召回，避免新写法漏判 |
| 条件匹配度 | `web/nlq.py` 的 `MATCH_WEIGHTS` | `match = Σ(命中条件权重) ÷ Σ(条件权重之和)`；权重 行政区 0.30 / 等级 0.25 / 类型 0.20 / 所有制 0.15 / 来源 0.10。**只反映与条件的吻合程度，不代表机构实力或好坏** |
| Haversine 球面距离 | `web/app.js`、`web/app.py`、`web/nlq.py` | 前端即时算距离保证手感，后端用于排序与分页 |
| 地址解析五级降级 | `resolveBase` → `matchInstitutionBase` → `geocodeAddress` → `locateMe` → `autoLocate` | 地标 → 我的位置 → 区中心 → 高德 geocode → 机构名兜底；未设基准点时距离文案降级为「距市中心」 |
| 维度统计 | `web/nlq.py` 的 `run_stats` + `/api/statistics/<dim>` | 5 个维度（行政区 / 等级 / 类型 / 所有制 / 协作网络），返回分组 + 占比 + 极值组 + 文字结论 |
| 生成式总结三级降级 | `genSummary` → `dim_ai_cache` → 本地模板 | 大模型 → 结果缓存 → 本地模板，**保证网络失败时绝不空白** |
| 地图 ↔ 列表悬停互指 | `SCATTER_IDX` + `ROW_EL_BY_ID` + `dispatchAction`（含去抖） | 9,678 点位下仍能无损联动 |

## 八、部署与运行

### 8.1 环境要求

- macOS（Apple Silicon）或 Linux，Docker 24+、Docker Compose v2
- Python 3.13（治理与构建脚本）、Node 22（仅前端构建辅助）
- 内存建议 ≥ 8 GB（Spark 容器 4 GB + HDFS + MySQL）

### 8.2 从零到跑起来（7 步）

```bash
# 1. 启动 5 个容器
docker compose up -d

# 2. 治理数据入湖到 HDFS（ODS 原始层，含行为日志导出）
python3 etl/upload_to_hdfs.py

# 3. 数仓全链路：ODS → DWD → 五维度分析 → ADS 落 MySQL（默认单机模式）
bash spark/run_all.sh

# 4. 重建查询索引（落库是 overwrite，索引必丢，此步必做）
python3 etl/create_indexes.py

# 5. 重建单文件前端快照与三份产物
bash web/build_spa.sh

# 6. 构建 Vue 前端（前后端分离形态 → web/vue/dist，Flask 挂载在 /spa/）
bash web/vue/build.sh

# 7. 启动 Web 服务
bash web/start.sh          # Vue: http://localhost:5001/spa/   离线单文件: http://localhost:5001/
```

> 第 6 步只有在改动 `web/vue/src/` 后才必须重跑；`web/vue/dist/` 已入库，
> 只 clone 不改前端的话直接进第 7 步即可访问 `/spa/`。

### 8.3 两种运行模式

```bash
# 默认：单机模式（Driver 在本容器内多线程并行）
bash spark/run_all.sh

# 可选：Standalone 集群模式（同一份代码、同一份 Maven 坐标，仅换 --master）
```

五类判据都是「看着乱」的可量化定义：

| 判据 | 定义 | 本轮修前实测 |
| --- | --- | --- |
| 溢出 | 出现横向滚动条，或元素 `overflow:visible` 却比容器大 | 整合页 1080 宽下左栏被挤到 **36px** |
| 参差 | 同一行的面板高度不一致 | 质量页首行 314 / 461，差 147px |

页面用 ECharts 空桩：版面只由 CSS 决定，桩掉图表既快又不受动画干扰。
「容器高度为 0」本身就是 CSS 决定的，所以空桩页照样查得出来。
断点两侧（1180 / 900）都取到了宽度，避免「断点附近才出问题」的情况漏检。

#### ⑤ 空板：最像"没数据"的故障，其实数据全在

**症状**：数据总览页「办别构成」面板只有标题和一块空白，看上去像"这个维度没有数据"。

**真相**：数据一个都不少。探针实测 `clientHeight=0`、canvas 存在但高 0、
`getOption().series` 里 **3 个数据点齐全**（公立 3,085 / 民营 5,323 / 未标注 1,381）。
ECharts 不报错、不警告：容器高 0 时它照样 `init`、照样 `setOption`、`series` 里也有数据，
只是画在一张 0 像素高的画布上。

**根因**：本项目的图表容器靠三种方式拿到高度 ——

1. 列进 `#ch1,#ch2,…{width:100%;height:100%}` 这份 **id 清单**（`.panel.sm` 给了固定 262px，`height:100%` 才解得开）
2. 带 `.achart` 类（`.achart{flex:1;width:100%;min-height:0}`，如质量页 `#ch_qcoord`）
3. `#map` 自己的 `flex:1`

`#ch_ov_own` 三种都不是 —— 它的 id 从没写进清单。**这是唯一一个漏登记的容器**
（全项目 33 个容器目标里，其余 32 个都合格），所以只有这一个面板是白的。

**修法**：把 `#ch_ov_own` 补进 id 清单，并在清单上方写清「新增图表必须同时改三处」：
清单 / `resizeAll()` 数组 / 空态↔有数据的 `setOption(opt, true)`。

**闸门的两个方向**（静态，不依赖渲染）：

- `图表容器 id 均已登记高度来源`：凡 `echarts.init` 用到的 id，若 HTML 里有元素却既不在清单、也不带 `.achart`、也不是 `#map` → 报红。
  id 是从 `web/app.js` 里扫的，三种写法都认：`mk('ch_own')`、`echarts.init($('ch1'))`、
  以及最易漏的 `const qc = $('ch_qcoord'); … echarts.init(qc)`（id 只出现在 `$()` 里，不看变量绑定就扫不到）。
- `HTML 图表容器均有 JS 初始化`：反向查 —— HTML 里 `id^="ch"` 的容器若没有任何 JS 去 init（改了 id 忘改 JS），也报红。

**运行时**：每档宽度下依次切过四个视图，量所有 `ch*` 容器的 `clientWidth/clientHeight`，任一为 0 即报红。

**反向测试**：R4 把清单里的 `#ch_ov_own` 删回去 → 6 项报红（5 档运行时 + 1 项静态）；
R5 只把 HTML 的 `id="ch_ov_own"` 改成 `ch_ov_own2` → `HTML 图表容器均有 JS 初始化` 报红。

> 这道闸门写出雏形后立刻抓到一个**只在特定宽度出现**的真缺陷：
> 整合页在 ≤1180px 会塌成单列（既有断点），而本轮新加的 `grid-column:2` 在「只有 1 条显式轨道」时
> 会**创建一条隐式列**（宽度 auto）—— 实测 1080 宽下隐式列吃掉 936px、`1fr` 那一列被挤到 36px，
> 左栏内容全部溢出面板。修法是在塌陷断点处成对重置 `grid-column` / `grid-row`。
> 教训：**凡是「显式网格定位 + 会塌成单列的断点」，塌陷处都要成对重置定位。**

#### ⑥ 图形形态：每张图用它最擅长的形态

**起因一（2026-09-21）**：用户看了医疗资源分析页，反馈「都是条形图」。实测确实如此 ——
15 张图里 **12 张是条形系**（横条 6 / 柱状 3 / 堆叠柱 3），只剩 2 饼 + 1 雷达。
当时的解法是按图形语义逐张换形，并把「形态 ≥11 种」写进闸门。
（那只雷达后来也因子指标口径不可比被换成「区域资源禀赋矩阵」，见起因四。）

**起因二（2026-09-22）**：用户再反馈「不够直观，像为了多样化而多样化，我的目的是使系统可用性更高」。
复盘发现，为凑形态换的那 5 张恰恰是最难读的：

| 图 | 当时的形态 | 实测读起来的问题 |
|---|---|---|
| 等级 × 办别 | 旭日图 | 12 个扇区摊到 1,289 家参评机构（当时口径；现为 874 家），多格只有个位数、外环宽不到 8px，白字标签压在同色浅块上 |
| 机构类型 × 办别 | 矩形树图 | 面积编码不可比；小类型压成窄带、标签截断成「卫生服务…」，右下角一列小块无法辨认 |
| 重点专科分级 | 棒棒糖 | 断崖分布下 166 与 77 两个圆点紧贴纵轴几乎重叠；横轴刻度挤成 `1,0002,0003,000…` |
| 专科级别对比 | 桑基图 | 只有 4 等级 → 2 级别，右侧永远两个节点，整块面积被一条流带占满、大片空白 |
| 数据整合深度 | 漏斗图 | `minSize: '22%'` 把 0.7% 的末档画成 22% 宽 —— 宽度与占比脱钩，而这张图只能靠宽度传达信息 |

**结论：图形形态服务于「这张图要回答的问题」，不是服务于「形态多样性」。**
五张全部改回条形系（旭日 / 树图 → 堆叠条形，棒棒糖 / 漏斗 → 条形），逐张解析见 README
「分析页可视化形态回调」条目。

**起因三（2026-09-22 下午）**：用户再反馈这两张「办别构成」图「太丑，未达到可视化的目的」。
对着数据核完，确认是两个设计缺陷叠在一起：

| 缺陷 | 现象 | 修法 |
|---|---|---|
| **图的维度 == 筛选维度** | 筛「三级」后「等级 × 办别」只剩一行，图不再提供任何信息 | `anSubset(except)` **自筛选豁免**：忽略自身那一维的条件，始终显示完整分组，并把当前行加粗 |
| **量级差 115 : 1** | 诊所 3,211 家 vs 体检中心 28 家，线性轴上后几名只有 1~3px，成了「发丝」 | 改 **100% 构成条**（段长 = 办别占比），行标签写「名称 · N 家」补回量级 |

**结论二：分组图的维度不能同时是筛选维度（否则一筛就塌）；量级悬殊时该用「构成条」，不该用「长度条」。**

**起因四（2026-09-22）**：用户看 03 段「空间格局」后问「这部分可视化或者数据是否有问题」。
查出来**数据真有问题**，而且分成两层：

| 层 | 问题 | 修法 |
|---|---|---|
| **数据** | 矩阵里大兴区「一级」= **369 家**（三级机构只有 11 家）。根因是 `etl/clean_merge.py` 的**文件名兜底**正则把《大兴区一级**以下**医院名单…》里的"一级"当成了等级，整份 318 行被盖上「一级」（313 家是诊所/医务室/门诊部）；《丰台区**村一级**卫生室》同理。而三级/二级/一级是**医院**评审结论，这六类基层机构按各自《基本标准》以「诊疗科目」执业，本就没有等级建制 | ① 文件名兜底加否定上下文识别（`以下/以上/以内` 修饰、前置「村」字一律不取）；② 立判据函数 `level_not_applicable()`（与前端 `NO_DEPT_CAT` 同源），一次性修复 335 家，并**同步归位 `grade_scope`**（`layer_dwd.py` 靠它决定 `level_norm`） |
| **可视化** | **行序按「行合计」排** —— 等于把"基层机构多"读成"资源强"，大兴区因此被顶到最顶行；且分区提示没交代等级数据的**来源覆盖度**差异 | 行序改「三级 → 二级 → 一级」字典序降序；分区提示补上"等级取自各区上报名单、各区收录完备度不一" |

**结论三：排序字段必须与这张图想表达的"强"同向；一个维度的数据来源覆盖度不齐时，必须在图上披露，不能让它伪装成普查结果。**

**闸门分两段**（因为空桩页测不出图形类型）：

- **静态段**：从 `web/app.js` 的 `function pieOpt` 一直扫到 `initAnalyticsInteractions`，
  提取全部 `type:'xxx'`。**不再断言「形态 ≥11 种」**，改为两条：
  ① 逐张形态在真库页段钉死比对；② bar 之外仍须覆盖 `{pie, line, heatmap, gauge}`，
  即「占比 / 趋势 / 矩阵 / 单一比率」四类编码各有一张 —— 防止退化成纯条形。
  起点必须从 `pieOpt` 开始 —— 饼图的 `type` 写在 `pieOpt` 里，若从第一个分析图扫起会漏掉饼图。

  `getOption().series[0].type` 与预期字典（**这张表是硬约束**：谁被换成不合适的图形，这里就报红），
  另量 canvas 尺寸与「办别三色」是否等于主题令牌。

**为什么单列一条「模块级常量未捕获主题令牌」**：本轮换图时发现旭日图外环是七彩，
导出 `getOption()` 看到节点 `itemStyle.color` 全是 `null` ——
根因是 `const OWN_SERIES = [['公立', ACC2], …]` 写在模块顶层，而 `ACC2 / WARN / DIM`
要到 `loadTokens()` 运行时才有值，于是三个颜色在模块求值时就固定成了 `null`，
ECharts 拿到 `null` **静默回落到自带默认调色板**（不报错、不警告）。
这条断言扫描模块级 `const/let/var` 声明体，凡捕获主题令牌即报红；修法是把常量改成函数，调用时再取值。

**反向测试**：R7（用模块级常量捕获令牌）/ R8（把办别三色改用默认调色板色）照旧被抓；
R6（把某张图改成条形系之外的形态）现在由「逐图形态钉死」这条捕获。

### 关于 ③ 中 Hive 的取舍说明（需在答辩时主动说明）

本项目**未使用 Hive Metastore**，数仓建模完全由 **Spark SQL + HDFS Parquet** 承担。理由：

1. **职责重叠**：Hive 的核心价值是"用 SQL 管理 HDFS 上的表"，而 Spark SQL 已经具备等价的 Catalog 能力（`spark.sql` 直接 `CREATE TABLE ... USING parquet LOCATION 'hdfs://...'`），再叠一层 Hive Metastore 对本项目的数据规模（万级）没有实际收益，只会增加一个故障点。
2. **一致性**：全部数据处理集中在 Spark 一处，口径不会在"Hive 侧 SQL"与"Spark 侧 DataFrame"之间漂移。
3. **可扩展性**：如果后续需要 Hive，只需在 `spark-submit` 加 `--conf spark.sql.catalogImplementation=hive` 并把 DWS 层的建表语句从 DataFrame 写法换成 `CREATE TABLE` 即可，现有分层结构（ODS/DWD/DWS/ADS）无需改动。

**建议答辩表述**："数据预处理与分析使用 Spark 完成；数仓分层由 Spark SQL 建模在 HDFS 上，未额外引入 Hive Metastore，原因是职责重叠且本项目规模下无收益。如需 Hive，可通过开启 `spark.sql.catalogImplementation=hive` 平滑接入，分层结构不变。"
