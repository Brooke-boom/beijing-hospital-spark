# 系统运行流程（从零到跑起来）

> 本文说明本项目的**四种运行方式**，按"从简到全"排列。所有命令与输出均为 2026-09-10 在本机（Mac M1 / macOS）实测。  
> 只想看效果 → 用方式一（30 秒）；要答辩演示 → 方式一 + 方式二；要体现完整工程链路 → 方式三。

---

## 零、先理解：系统由哪几段组成

```
① 数据层   data/processed/master_institutions.csv   ← 9,678 家（数据中枢）
② 入湖层   HDFS /hospital/ods/raw                   ← 治理后 CSV + 行为日志（etl/upload_to_hdfs.py）
③ 计算层   spark/jobs/                              ← Spark 数仓作业，按分层 + 分析维度拆分（10 个阶段）
④ 存储层   HDFS /hospital（ODS/DWD/DWS 三层 Parquet）+ MySQL（3307，20 张表）
⑤ 服务层   web/app.py（Flask，默认 5001 端口）       ← 28 个路由（25 个 API），含自然语言筛选 /api/nlq/*
⑥ 展现层   在线：Vue 3 SPA（/spa/，1 条任务主线 + 4 个查阅支撑页）
           单文件：web/dashboard_offline.html      ← 零依赖单文件（10MB，查阅 + 智能筛选两形态）
```

**关键认知**：⑥ 单文件形态已经把数据内联进 HTML，所以它**不依赖 ②③④⑤**，双击就能用，
而且**主线同样可跑**——中文条件的解析与内联快照上的筛选、统计由 `web/app.nlq.js` 本地完成，
依据是构建时内联的词表（从 `web/nlq.py` 统一导出，禁止手抄）与机构快照。
两种形态的结果由 `etl/verify_offline_nlq.py`（351 项断言）逐字段比对，保证**不是两个系统**。

## 方式一：单文件形态（零依赖，30 秒）

**适用**：给老师/面试官演示、直接发给别人、快速查看效果、网络环境差。

```bash
# 直接打开（任选一种）
open web/dashboard_offline.html                      # macOS
# 或双击该文件
```

- 无需 Python、无需 Docker、无需数据库、无需联网；托管到任意静态空间（如 GitHub Pages）即可分享链接
- **两条线都能用**：
  - 「智能筛选」主线 —— 说一句话（"朝阳和海淀的三级医院"）→ 条件卡 → 真实数据结果；或直接选条件；说"按行政区统计"则切换为维度统计
  - 「查阅」分组 —— 七维筛选、五种排序、图表联动、详情抽屉、机构对比
- 主线的解析与查询由前端本地完成（`web/app.nlq.js`），与在线接口 `/api/nlq/*` 的结果**逐字段一致**，由 `etl/verify_offline_nlq.py`（351 项断言）把关
- **不支持**：数据实时更新（是构建时的快照）；会话留痕存数据库（改存浏览器本地）；AI 生成式总结

> ⚠️ 定位功能在 `file://` 协议下浏览器会拒绝授权。需要测定位请用方式二走 `http://`，
> 或在本机起一个静态服务（如 `python -m http.server`）。

## 方式二：启动 Web 服务（Flask + MySQL，推荐答辩用）

**前置条件**：MySQL 在 3307 端口已有数据（本项目由 Docker 容器提供）。

```bash
# 1. 确认数据库在（应返回 9,678）
docker ps --format '{{.Names}}\t{{.Status}}' | grep mysql

# 2. 启动服务
bash web/start.sh                    # 默认 5001 端口
# 换端口：PORT=8000 bash web/start.sh

# 3. 浏览器打开（两种形态都在同一个服务里）
open http://localhost:5001/spa/      # Vue 3 前后端分离形态（推荐）
open http://localhost:5001/          # 单文件大屏（Flask 渲染版）
```

> 若 `web/vue/dist/` 不存在，`/spa/` 会返回 503 并提示构建命令。
> 只 clone 不改前端的话产物已在仓库里，可直接访问。

**实测验证**（四条命令确认真的跑起来了）：

```bash
curl -s http://127.0.0.1:5001/api/health
# -> {"institutions":9678,"status":"ok"}

curl -s "http://127.0.0.1:5001/api/institutions?district=海淀区&level=三级&page_size=2"

curl -s -o /dev/null -w "status=%{http_code}\n" http://127.0.0.1:5001/
# -> status=200

curl -s -o /dev/null -w "spa=%{http_code}\n" http://127.0.0.1:5001/spa/
# -> spa=200
```

### 方式二·附：Vue 前端的开发与构建

```bash
# 开发模式（Vite HMR，热更新，/api 自动代理到 Flask:5001）
bash web/vue/build.sh --dev
#   → 打开 http://127.0.0.1:5173/spa/   改 src/ 下的文件即时生效

# 生产构建（改完前端源码必做，否则 /spa/ 还是旧页面）
bash web/vue/build.sh

# 构建后建议跑一次产物校验 + 端到端冒烟
python3 etl/verify_artifacts.py     # 三份单文件产物 + Vue 产物
python3 etl/smoke_vue.py            # 需 Flask 在跑；7 路由 / 0 报错
```

> ⚠️ **Flask 必须重启**才能生效的后端改动：改了 `web/app.py` 要重启服务
> （`pkill -f "web/app.py"` 后重新 `bash web/start.sh`），否则新路由 404。
> 前端改动则不需要重启 Flask，重新构建即可。

**停止服务**：`Ctrl+C`（若后台运行则 `pkill -f "web/app.py"`）

> 💡 若 MySQL 未启动，脚本会警告但**仍会启动 Flask**，此时接口会报数据库连接错误。看到警告先 `docker compose up -d mysql`。

## 方式三：Docker Compose 全栈（完整工程链路）

**适用**：从零重建、演示"数据处理→存储→服务"全过程、写进简历的部署实践。

```bash
# 1. 启动 HDFS + Spark 集群 + MySQL（首次会拉/构建镜像，约几分钟）
docker compose up -d

# 2. 确认容器状态
docker compose ps          # 应见 hdfs-namenode / hdfs-datanode / spark-master / spark-worker / hospital-mysql 五个 Up

# 3. 数据入湖：治理后 CSV + 用户行为日志 → HDFS /hospital/ods/raw
python etl/upload_to_hdfs.py

# 4. 提交数仓全链路作业（ODS → DWD → 5 个分析维度 → ADS → MySQL）
bash spark/run_all.sh
#   等价于容器内：
#   spark-submit --master spark://spark-master:7077 \
#     --conf spark.jars.ivy=/opt/workspace/jobs/.ivy2 \
#     --packages com.mysql:mysql-connector-j:8.4.0 \
#     /opt/workspace/jobs/jobs/run_all.py
#   单独重跑：bash spark/run_all.sh --only ads / --from space

# 5. 【必做】重建查询索引（落库的 overwrite 模式会 DROP+CREATE 表，索引会全丢）
python etl/create_indexes.py

# 5.5（可选 · 历史遗留）旧导诊知识库维度表——主线筛选不依赖它，仅复查历史数据时执行
python etl/build_disease_dept_map.py     # 生成 data/processed/disease_dept_map.csv（417 条 / 29 科室）
python etl/load_disease_dept.py          # 写入 MySQL 维度表 dim_disease_dept

# 6. 【必做】重新生成快照与离线大屏
bash web/build_spa.sh

# 7. 启动 Web 服务
bash web/start.sh
```

**可视化管理界面**：

- HDFS NameNode UI：<http://localhost:9870>（Browse the file system → `/hospital` 可逐层查看 ODS/DWD/DWS）
- Spark Master UI：<http://localhost:8080>
- Spark Worker UI：<http://localhost:8081>

**HDFS 分层核验（答辩现场可演示）**：

```bash
docker exec hdfs-namenode hdfs dfs -ls -R /hospital | head -30
docker exec hdfs-namenode hdfs dfs -du -s -h /hospital/ods/raw /hospital/ods/parquet /hospital/dwd /hospital/dws
# 读一份 Parquet 的前几行（验证是真实列式数据，不是空目录）
docker exec hdfs-namenode hdfs dfs -ls /hospital/dwd/dwd_institution_clean | head
```

**前端大屏（http://localhost:5001）视图导航**：

- 「数据总览」：4 张 KPI + 北京 16 区分级地图（点击区县联动筛选）+ 类型/等级/办别图 + 数据来源与质量概览条。
- 「医疗资源分析」：八维分析图表（办别 / 重点专科分级 / 协作网络 / 等级×办别 / 专科能力 TOP10 / 区域×等级 / 坐标精度 / 科室覆盖 TOP15）+ 四项 KPI，**全部随七维筛选实时联动**。
- 「机构查询」：七维筛选 + 机构列表（勾选对比 / 收藏 / 分页）+ 机构详情抽屉。
- 「智能筛选」：自然语言输入 → 条件解析 chips + 排序单选 + Top 5 预览 → 一键跳转机构查询完整结果。
- 「数据整合」：三类数据源构成 + Spark 处理流程时间线 + 整合结果 + ETL 批次时效表。
- 「数据质量」：字段完整率（8 项）+ 坐标精度分布 + 去重与多源交叉验证 + 清洗后类别构成。
- 「系统说明」：数据规模、公开数据来源、Spark 清洗流程、数仓分层表清单、更新时间与更新日志。
- 切换逻辑：左侧 `.sidebar` 七个 `navtab` 切换 `.view` 显隐，切到隐藏视图时图表 `resize()` 重算尺寸（ECharts 隐藏容器初始化尺寸为 0，必须切回可见后 resize 才正常渲染）。

## 方式四：数据更新链路（源数据变了怎么走）

用于"我改了源 CSV / 新增了治理字段"的场景，按顺序执行：

```bash
# ① 离线治理（办别 / 子类 / 擅长分级等）→ 更新 master_institutions.csv
python etl/govern_master.py

# ② 整合协作网络维度（net_* 字段）→ 主表 / wide 表 / MySQL 三层同步
python etl/integrate_networks.py

# ③ 机构更名同步（如有）
python etl/fix_renamed_institutions.py

# ④ 数据入湖（治理后 CSV + 行为日志 → HDFS）
python etl/upload_to_hdfs.py

# ⑤ 数仓全链路（ODS → DWD → 五维分析 → 科室实力指数 → ADS → MySQL）
bash spark/run_all.sh
#   ⚠️ 只改了 ④ 之后的层：bash spark/run_all.sh --from dwd
#   ⚠️ 但 ⚠️ 改过源 CSV 后重跑必须用 --from ods！--from dwd 会复用旧的 ODS Parquet，
#      出现"改了数据却没生效"的假象（实测踩过：协作网络新增成员没进 ads_dept_strength）
#   ⚠️ ads_dept_strength 属下线主线遗留（前端已无引用），仅在复查历史数据时才需要重跑该阶段
bash spark/run_all.sh --only deptstrength

# ⑥ 重建索引（⑤ 之后必做）
python etl/create_indexes.py

# ⑥.5（可选 · 历史遗留）旧导诊知识库（若 disease_dept_map.csv 调整过）
python etl/build_disease_dept_map.py && python etl/load_disease_dept.py

# ⑥.6 端到端冒烟（智能筛选页 + 全站路由）与版面校验
python etl/smoke_nlq_ui.py && python etl/smoke_vue.py
python etl/smoke_dashboard.py && python etl/verify_layout.py

# ⑦ 重建快照与离线大屏
bash web/build_spa.sh

# ⑧ 提交（web 产物入库）
git add web/dashboard_offline.html web/templates/index.html && git commit -m "..."
```

> 📌 步骤 ⑤⑥⑦ 顺序不能乱：先跑数仓落库 → 再建索引 → 再从库抽快照。

## 常见问题（实测踩过的坑）

| 现象                                | 原因                                     | 解决                                                     |
| --------------------------------- | -------------------------------------- | ------------------------------------------------------ |
| 端口 5000 起不来                       | macOS AirPlay Receiver 占用 5000         | 用默认 5001，或 `PORT=8000 bash web/start.sh`               |
| MySQL 连不上                         | 容器未启动，或 3306 被本机 MySQL 占用              | 容器映射到 **3307**；`docker compose up -d mysql`            |
| `docker: command not found`       | Docker Desktop 已装但 CLI 不在当前 PATH（沙盒常见） | 用 `/usr/local/bin/docker`，或把 `/usr/local/bin` 加入 PATH  |
| Flask 起来了但接口报错                    | MySQL 无数据（没跑过 ETL）                     | 走方式三第 3 步；`/api/health` 应返回 9678                       |
| 查询变慢                              | ETL 后索引被清掉了                            | 重跑 `python etl/create_indexes.py`                      |
| 建索引报 error 1170                   | Spark 建表字符串列是 TEXT，MySQL 禁直接建索引        | 脚本已用前缀索引，勿手工改                                          |
| 定位功能不弹授权                          | `file://` 协议被浏览器拒绝                     | 用方式二走 `http://localhost:5001`                          |
| 换台机器跑 `build_spa.sh` 报 python 不存在 | 脚本硬编码了本机 Python 绝对路径                   | 把 `/Users/brooke/.workbuddy/.../python` 换成你的 `python3` |
| 大屏数据还是旧的                          | 浏览器缓存                                  | `Cmd + Shift + R` 硬刷新                                  |
| **改完前端、`build_spa.sh` 也跑了，页面还是旧版** | Flask 的 Jinja 模板在 `debug=False` 下会缓存在内存 | 已在 `app.py` 设置 `TEMPLATES_AUTO_RELOAD=True`；若仍不行则重启 Flask |
| 地图上的诊断横幅（"地图就绪"）看不到             | ECharts/zrender 初始化会清空容器 `innerHTML`     | `#map_diag` 必须放在 `#map` **外面**（现为 `.mapstage` 的兄弟节点）      |
| 运营后台「用户行为分析」全是"暂无数据"           | 埋点表 `fact_user_event` 尚无记录（冷启动正常）      | 用一阵子（搜索 / 筛选 / 导诊 / 查看详情）即自动累积；想清空见下方说明   |
| 详情抽屉「周边配套」一直转圈或为空              | 高德 Key 未配置 / 额度用尽 / 断网                | 检查 `data/.amap_key.txt`；离线单文件不支持该功能（会明确提示）          |
| 抽屉「实时状态」是否真实                      | 不是，是**演示模拟数据**                        | 界面上已明确标注"演示模拟"，真实号源以 114 平台为准                        |
| HDFS 写入报 **Permission denied**    | Spark 容器进程 uid=185，HDFS 按 POSIX 校验      | 已在 compose 给 spark 服务设 `HADOOP_USER_NAME=root`；如手工起容器需自行透传该变量 |
| `hdfs dfsadmin -report` 显示 **Live datanodes (0)** | DataNode 未起来或与 NameNode 版本不匹配        | 等 10~20 秒再查；仍为 0 则 `docker logs hdfs-datanode` 看报错          |
| spark-submit `--packages` 报 ivy 目录不可写 | 默认 `~/.ivy2` 在镜像内不可写（用户 spark 无家目录）   | 已统一加 `--conf spark.jars.ivy=/opt/workspace/jobs/.ivy2`（`spark/run_all.sh` 内置） |
| NameNode 反复重启                        | 首次启动格式化失败（`/data/dfs/name` 残留脏数据）      | `docker compose down && docker volume rm hospital-spark_hdfs-namenode` 后重启（会清空 HDFS 数据，需重新入湖） |

## 行为日志与运营统计（v4.0 引入；独立页面于 v5.0 信息架构重构下线，接口保留）

原「运营后台」页分两块，页面下线后 `/api/admin/stats` 接口与埋点链路完整保留：

1. **用户行为分析** —— 数据来自真实埋点表 `fact_user_event`。埋点由前端 `track()` 触发（搜索关键词 / 筛选区域 / 导诊病情 / 查看详情 / 对比 / 定位 / 自然语言解析），后端 `/api/track` 只做一条 `INSERT`，**失败静默**，绝不影响主流程。冷启动时为空属正常，使用一段时间后自动累积。
2. **资源热度分析** —— **完全由前端本地快照计算**，与用户行为无关，冷启动即有内容（区县密度 / 等级构成 / 专科覆盖 / 网络覆盖 / 办别构成 / 类型构成）。

```bash
# 查看埋点累积情况
docker exec hospital-mysql mysql -uroot -phospital123 hospital \
  -e "SELECT ev, COUNT(*) n FROM fact_user_event GROUP BY ev ORDER BY n DESC;"

# 想清空行为日志、重新做一场干净的演示（可选）
docker exec hospital-mysql mysql -uroot -phospital123 hospital \
  -e "TRUNCATE TABLE fact_user_event;"

# 清空高德 POI 缓存（换了医院坐标或想强制重新查询时用）
docker exec hospital-mysql mysql -uroot -phospital123 hospital \
  -e "TRUNCATE TABLE dim_poi_cache;"
```

> 埋点表 `fact_user_event`、POI 缓存表 `dim_poi_cache` 由 Flask 首次调用时自动 `CREATE TABLE IF NOT EXISTS` 建好，
> **不参与 Spark ETL**，因此重跑 ETL（`mode=overwrite`）不会影响它们。

## 可选：启用 Agnes 大模型兜底

自然语言筛选的**主路径是本地规则引擎**（`web/nlq.py` 的词表 + 正则，完全离线可用），
只有规则零命中时才调用大模型做兜底解析，属于可选增强——不配也能正常演示。

**配置密钥**（三选一，优先级从高到低）：

```bash
# 方式 A：环境变量
export AI_API_KEY=sk-xxxxxxxx

# 方式 B：密钥文件（推荐；已被 .gitignore 排除，不会入库）
echo 'sk-xxxxxxxx' > data/.ai_key.txt && chmod 600 data/.ai_key.txt

# 方式 C：完全关闭，退回纯离线模式
export AI_LLM_ENABLED=0
```

可选覆盖：`AI_API_BASE`（默认 `https://apihub.agnes-ai.com/v1`）、`AI_MODEL`（默认 `agnes-2.0-flash`）、`AI_TIMEOUT`（默认 10 秒）。

**验证是否接通**：

```bash
curl -s "http://127.0.0.1:5001/api/ai/health"           # 看 llm_enabled
curl -s "http://127.0.0.1:5001/api/ai/health?probe=1"    # 真实调用一次模型
```

**演示前预热（重要）**：Agnes 免费额度实测约 **1 次 / 30~40 秒**，现场连续提问会触发 429 限流。提前把常用问法跑一遍写入缓存，现场就是零等待：

```bash
bash web/start.sh                      # 先起服务
python etl/warm_ai_cache.py            # 预热内置的 8 条口语长尾问法（约 4 分钟）
python etl/warm_ai_cache.py --queries "手抖还瘦了很多|眼睛干涩发痒"
```

- 结果存在 MySQL `dim_ai_cache` 表，**重启服务依然有效**；本地知识库已覆盖的问法会自动跳过（`skipped_local`），不浪费额度。
- 缓存三层：内存 → MySQL → 接口。实测同问第二次 **0.05 秒**返回（首次约 3.6 秒）。
- 限流时接口会明确返回「Agnes 免费额度限流，稍后重试即可」，**本地知识库链路不受影响**。
