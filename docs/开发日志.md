### 关键决策记录
| 决策点 | 结论 | 理由 |
|---|---|---|
| 计算引擎 | Spark 3.5.3（PySpark） | 满足毕设"大数据"定位；官方镜像原生支持 arm64 |

- **去重合并**：规范化机构名（去空格/统一括号/去"北京市"前缀）作为归并键；按字段丰富度择优合并；`src_count` 记录多源交叉验证次数。原始 13,803 条 → 9,791 家。

## 2026-09-11（收尾）：仓库同步校验工具 + 补齐遗漏提交

### 问题
本项目用 GitHub Git Data API 提交（沙盒内 `git push` 不可用），commit/tree/blob 对象只存在远端，本地 `.git/objects` 缺这些对象，导致 **`git status` / `git diff` 直接报 `fatal: bad object HEAD`**，无法判断"有没有改动没推上去"。此前几轮改动因此存在**静默漏推**：`docs/开发日志.md`、`docs/数据联网核实报告.md` 的本地更新一直没进远端。

### 方案
新增 `etl/api_verify_sync.py`：绕开本地对象库，直接拉远端 tree，把每个 blob 的 SHA 与本地文件重算的 git blob SHA 逐字节比对。依赖两个仍可用的本地 git 能力：`git ls-files -z`（跟踪清单）与 `git ls-files -o --exclude-standard -z`（未跟踪且未被忽略的新文件）。

**关键设计**：本地索引在 API 提交后**不会更新**，所以"未跟踪"清单里会混入大量其实早在远端的文件。因此必须以**远端 tree 作为权威清单**做二次过滤，否则误报一片（首版就误报了 17 个）。

### 首次运行发现的问题
- `docs/开发日志.md`、`docs/数据联网核实报告.md` 本地有未推送改动（对照远端 diff 确认为正常演进，非误改）。
- `docs/答辩与简历讲解手册.md` 属"防抄袭不入库"材料，但**没在 `.gitignore` 里**，存在被误提交的风险 → 已补规则。
- 4 个一次性提交脚本 `etl/api_commit_*.py` 属临时脚手架，已加 `.gitignore` 规则（通用工具保留为 `etl/api_verify_sync.py`）。
- 密钥扫描：全仓正则扫 `sk-*` / `ghp_*` / `github_pat_*`，无命中。

### 经验
**"推送成功"不能靠 `git push` 的输出判断。** 本环境里 `Everything up-to-date`、fatal 报错、后台任务 failed 都不可信。唯一可靠判据是**把远端内容和本地内容逐字节比一次**——这也是这个校验脚本存在的意义。日常收尾固定跑一遍 `python3 etl/api_verify_sync.py`。

**修复**：`svgIcon()` 返回值 `+ p +` → `+ '<path d="' + p + '"/>' +`；`dashboard.html` 10 处静态 SVG 用正则 `<svg class="ic"([^>]*)>([^<]+)</svg>` → `<svg class="ic"\1><path d="\2"/></svg>` 统一包裹。
**顺带修掉两处**：① logo `fill="currentColor" stroke="none" style="color:var(--acc)"` = 蓝底画蓝图标（自隐），改为 `fill="none" stroke="currentColor"`，用 `.mark` 的深色 `#0a0b0d`；② 遗留的 `.ic{width:14px;height:14px;…}` 与新版 `.ic{width:16px;…}` 冲突（后者在前会输），删掉遗留规则。

### 三、导诊"AI 说话"深化（本轮最大亮点）

1. **把 echarts 脚本块整体换成空桩**（`{init:()=>({setOption,resize,dispose,on,…}),registerMap(){}}`），app.js 全初始化路径即可在 4 秒内跑完并 dump；
2. 末尾追加探针脚本，把断言写进 `document.title` 再 grep（比翻 6MB DOM 高效得多）。
实测结果：`rows=20 / rowstar=20 / presets=6 / iconbtn=2 / svgic=62 / svgpath=62 / flt_count=命中 9,789 / 9,789 家 / ERR=none`；交互链路（预设→chips→收藏→收藏夹→全部加入对比→AI 总结→重置）逐项通过。
另：`Read` 可以读图，静态骨架（CSS + body 去 script，取**主 `</style>` 之后**的 body）渲染截图目视确认了筛选区分组、预设条、已选条件 chips、列表星标、收藏夹卡片、麦克风图标。

### 经验
1. **"离线可用"必须覆盖新增的 AI 能力**：语音（file:// 禁麦克风）与生成式总结（无网络）都要有明确降级路径 —— 前者给指引、后者用本地模板，绝不静默失败或留白。
2. **纠错要"可见"**：纠错结果必须以提示形式回显（"已把「朝杨区」理解为「朝阳区」"），否则用户不知道系统改了他的词。
3. **预设是切换不是叠加**：多条件预设必须先复位再套用，并做反向判定点亮，否则状态会越点越乱。
4. 本环境 headless Chrome 遇 ECharts 动画会挂死 → 用"脚本打桩 + title 探针"验证前端初始化路径；`timeout` 在 macOS 不存在，用 `timeout` 会得 `127` 造成误判。

## 2026-09-14（下午·二）：白天/黑夜双主题 + 筛选区二次收敛 + 地图列表联动

### 一、双主题（白天 / 黑夜，黑夜为默认）
原样式把颜色写死在 90 余处规则里，无法整体换肤。做法是**只换令牌层，组件层零分支**：

1. **色相族变量化**：把 `rgba(107,140,255,.14)` 这类「同一色相不同透明度」的写法统一改为 `rgba(var(--acc-rgb),.14)`，新增 `--acc-rgb / --crit-rgb / --warn-rgb / --teal-rgb / --vio-rgb / --hair-rgb` 等通道变量。浅深两套主题只需换通道值，透明层级完全复用。
2. **语义前景令牌**：`--t-crit-fg`（浅底 tint 上的红字）、`--on-accent`（实色主色底上的字）、`--ink-strong`（hover 强调字）、`--tint-fg`（tint 圆底上的图标）、`--veil / --veil-2 / --scrim / --drawer-sh`（浮层与遮罩）等——这些是「同一个色相在两个主题下要往相反方向走」的地方，必须单独给令牌，否则白字在浅色底上直接消失。
3. **`:root[data-theme="light"]` 覆盖块**：白天主色不是简单调亮，而是**加深**（`--acc:#3a5bd9`）保证白底上的对比度；`--ink-4` 也由 `#4c4e57` 反转为 `#9aa0ab`。
4. **首帧防闪**：`<style>` 之后紧跟一段内联脚本读 `localStorage.bjyy_theme` 并落定 `data-theme`，避免先画黑夜再跳白天。
5. **图表随主题重绘**（这块最容易漏）：ECharts 的颜色是喂给 canvas 的，**不能写 `var(--x)`**，必须由 JS 读出实值。故 app.js 里原来的 `const INK = '#ededee'` 等常量全部改为 `let` + `loadTokens()` 集中装载（`getComputedStyle` 取 CSS 变量，自定义属性会返回 var() 替换后的实值）；`AXIS / TIP / LEGEND / LV_COLOR` 也在装载时重建。切主题调用 `applyTheme()`：换 `data-theme` → `loadTokens()` → `drawMap() + updateCharts() + updateAnalyticsCharts() + renderKPI/renderList/renderFilterChips` → 抽屉若开着则重开。
6. 地图底图从 `initCharts()` 里**抽成独立的 `drawMap()`**，否则切主题时地图配色永远停在首次渲染那一刻。

### 二、筛选区二次收敛（用户反馈"还是太杂乱"）

## 2026-09-15（11:00-12:30）：架构补齐 HDFS 全链路 + 分析代码按维度拆分

### 背景
指导老师复盘标准明确了五条硬要求，其中两条与既有架构正面冲突：
① 数据存储必须依托 HDFS（分析读的数据应从 HDFS 来）
② 数据预处理的结果必须回写 HDFS
③ 预处理/分析必须使用大数据技术（Spark、Hive），提示"Maven 单机 Spark 依赖"
④ 分析结果保存到业务数据库（MySQL）
⑥ 分析代码按维度划分（时间维度、空间维度……）

改造前：原始 CSV 走本地只读卷，ODS/DWD/DWS/ADS 全部落 MySQL，**完全没有 HDFS**；
单脚本 407 行的 `spark/etl_hospital.py` 承担全部逻辑，无维度模块；依赖用 `--jars` 手工挂 jar。
改造后：**HDFS 承载 ODS/DWD/DWS 三层 Parquet，MySQL 只存 ADS 服务层结果**；作业按分层 + 五维拆分。

### 一、存储层：自建 arm64 HDFS 镜像
- 官方 `apache/hadoop:3.3.6` 只有 amd64，M1 上 QEMU 模拟起不来（实测启动即崩）。
  故在 `docker/hadoop/` 自建镜像：Temurin 11 JRE + Apache Hadoop 3.3.6 官方 tar 包，
  `HDFS_ROLE` 环境变量在同一镜像上分别拉起 namenode/datanode 两种角色。
- 坑：`docker compose build` 走 buildkit 时，对镜像加速器（daocloud）的 HEAD 元数据请求返回 **401**，
  导致 `FROM eclipse-temurin:11-jre-jammy` 解析失败。解法：先 `docker pull eclipse-temurin:11-jre-jammy`
  把基础镜像拉到本地，再用 `DOCKER_BUILDKIT=0 COMPOSE_DOCKER_CLI_BUILD=0 docker compose build` 走经典构建器。
- 目录规划：`/hospital/{ods/raw, ods/parquet, dwd, dws/{space,category,dept,network,time}, meta/snapshots}`。

### 二、Spark 接 HDFS 客户端
- 把 `core-site.xml` / `hdfs-site.xml` 以单文件卷挂进 `/opt/spark/conf`（该目录在 Spark 默认 classpath 上），
  比在 `--conf` 里逐条传 `spark.hadoop.*` 更干净。
- **权限坑**：Spark 容器进程 uid=185(spark)，HDFS 按 POSIX 校验会 Permission denied。
  解法：给 spark 两个服务加 `HADOOP_USER_NAME=root`（客户端以超级用户身份访问），保持 HDFS 权限校验开启。

### 三、数据入湖（etl/upload_to_hdfs.py）
- 7 个文件入湖：治理后主表/科室关系/科室字典/重点专科/地理编码/疾病知识库 6 个 CSV
  + 从 MySQL 导出的 `fact_user_event.csv`（41 条真实埋点，供时间维度分析）。
- 幂等：先 `-rm -f` 再 `-put`；校验：逐个比对 HDFS 文件字节数与本地一致（7/7 ✓）。
- 坑：`hdfs dfs` 的子命令必须带 `-`（`-ls`/`-put`），第一版写成 `ls`/`put` 直接报 Unknown command。

### 四、作业重构：按分层 + 分析维度拆分（spark/jobs/）
| 模块 | 职责 |
|---|---|
| `common.py` | SparkSession、HDFS 路径常量、Parquet/JDBC 读写封装 |
| `layer_ods.py` / `layer_dwd.py` | ODS 列式化；DWD 清洗 + 坐标关联（口径与原实现逐字一致） |
| `dim_space.py` | 空间维度：区县分布、坐标覆盖、区域重心、**16×16 区间 Haversine 距离矩阵**（256 条） |

| `dim_dept.py` | 科室覆盖度、科室×区分布、各区科室种类密度 |
| `dim_network.py` | 四类协作网络（儿科医联体 53 = 核心 7 + 成员 46、卒中 76、危重新生儿 8、危重孕产妇 20）|
| `dim_time.py` | 时间维度：行为日趋势/时段/功能结构 + 每批次 ETL 时效性快照（追加式） |
| `layer_ads.py` | 服务层：HDFS 分析结果 → MySQL（服务副本 + 应用宽表 + 新增分析结果） |

## 2026-09-16（12:20-13:00）：修复智能导诊「万金油」问题——排序改为科室优先

### 现象（用户反馈 + 截图）
连问「头痛发热 / 腹痛呕吐 / 尿频尿急 / 儿童持续咳嗽 / 皮肤过敏」五个不同病症，
推荐医院**完全相同**（同仁医院、隆福医院、北大医院、305 医院……），怀疑没接入大模型。

### 根因诊断（三条，均与 Agnes 无关）
实测 8 个病症后确认：**科室识别是准的**（感染科/神经内科、泌尿外科、皮肤科、口腔科、骨科
各不相同），问题出在**医院排序**：
1. **评分权重与导诊目标不匹配**：导诊沿用了主检索的「等级 0.5 / 距离 0.3 / 科室 0.2」。
   大型综合医院科室齐全 → `科室契合` 恒为满分 1.0，且等级最高，于是**任何病症都排出同一批三级医院**。
   科室这一维权重只有 0.2 且对大医院不产生任何区分度。
2. **默认基准点臆造位置**：用户未授权定位时，代码仍以 `DEFAULT_LNG/LAT`（天安门）当作"用户位置"
   参与距离打分，排序被悄悄偏移到基准点所在的东城区，顶端长期被同一片区的医院占据。
3. **重点专科信号几乎为空**：`dwd_dept_relation_clean.is_key_specialty` 全库仅 23 行为 '1'
   （16,251 行中），原有的 `key_bonus` 形同虚设。
4. **同院多院区重复占位**：同仁医院有 4 条记录（本部/东院区/南区两种写法），隆福医院 4 条，
   6 个推荐名额里常被同一家医院占掉 2 个。

> 澄清：Agnes 只在「本地知识库零命中」时兜底做**症状→科室**映射，医院排序全程不经过大模型，

- **真库版 headless 偶发虚拟时间不收敛**：同一页面 1440px 首次通过、复跑挂住（`dom=0B`）。
  解法：验证交互与断点时把 ECharts 换成**空桩**（页面 5.24MB），五档宽度一次通过；
  仅需真实图表外观时才用「注入 `animation:false`」的真库版。
- **探针输出被自己的过滤条件吞掉**：Chrome 挂住时 `dom=0B`，打印前先做 `startswith` 过滤，
  连「无输出」占位串一起滤掉，输出只剩空行，误判为"探针跑空"。应先打印原始返回长度。
- **`rfind` 返回 -1 时的切片退化**：定位探针用 `d[:k]`，若 `k=-1` 会退化成 `d[:-1]` 并静默产出坏页面；
  改用 `assert` 守住索引。
- **并行/多点替换的顺序依赖**：CSS 里同一选择器存在两处定义（旧版在中部、新版在末尾），
  改写时必须确认新规则位于其后，否则会被静默击穿。
