# 项目最终整改报告

> 课题：《基于Spark的北京市医疗机构资源整合与多维筛选可视化系统》
> 整改主题：**系统定位收敛 + 任务主线重构 + 数据可信度加固**
> 依据：项目负责人下发的《项目最终优化与重构总指令》
> 完成日期：2026-09-20 ｜ 整改后全量校验：产物 ✅ / 双端一致性 150 项 ✅ / 冒烟 47 项 ✅ / 运行时错误 0

---

## 一、整改缘起

系统在 2026-09-18 已完成技术架构的全部硬要求（HDFS 全链路、Spark 单机模式、Vue 前后端分离、双形态前端）。
但**功能定位**上存在一个必须纠正的偏移：主线被做成了「**就医决策工作台**」——用户输入症状，
系统分诊出科室并推荐医院、生成就医方案、提供挂号入口。

这条路线与课题名称《北京市医疗机构资源整合与**多维筛选**可视化系统》不符，且带来三个真实风险：

| # | 问题 | 风险 |
|---|---|---|
| 1 | **定位越界** | "输入症状 → 推荐医院"本质是就医引导，与课题的"资源整合 + 多维筛选"不是同一件事；答辩时无法自证与本课题的相关性 |
| 2 | **边界风险** | 大模型参与判科与推荐，等于让系统对医疗问题给出建议，而本项目**没有任何患者诊疗数据**——这是拿没有的数据回答不该回答的问题 |
| 3 | **可信度风险** | 部分统计口径散落在前端常量与模拟数据中（候诊状态、号源参考等演示字段），与"统计数字必须来自数据库"的要求相悖 |

本轮整改的目标因此不是"再堆功能"，而是**把系统收敛回它本来的样子**：
一个面向北京医疗机构**资源数据**的分析与筛选平台，不诊断、不导诊、不推荐就医。

| 维度 | 整改前 | 整改后 |

## 三、逐项整改明细

### 3.1 定位与命名收敛

- 全文案口径统一为「**机构资源数据的查询与筛选**」；"就医决策""智能导诊""分诊""推荐医院"等表述从界面、接口注释、关于页、运营后台中清除（仅**开发日志与更新日志的历史条目**保留原样，用于记录能力演进，并在条目内标注"已于 2026-09-20 下线"）。
- 关于页「数据来源」剔除**北京市预约挂号统一平台（114）**——它不是本系统的数据来源，只是外链入口；机构详情抽屉中保留该外链，但明确标注"官方信息入口 · 外链跳转，本系统不抓取号源与排班"。
- 前端侧边栏主任务项由「就医决策」改为「**智能筛选**」。

### 3.2 任务主线重构：自然语言智能筛选

**一句话 → 条件 → 真实数据**，这条链路是整改后的全部主线：

| 环节 | 实现 | 关键约束 |
|---|---|---|
| ① 理解中文 | `web/nlq.py`（834 行规则引擎）：分词、别名归一、错别字纠正（difflib）、意图判定（筛选 / 统计 / 拒答） | 完全离线，**不依赖大模型**；可复现、可解释 |
| ② 生成条件 | 解析结果是一组**可增删的条件卡**（行政区 / 等级 / 类型 / 所有制 / 来源 / 科室 / 关键词） | 用户须确认后才查询，解析错了当场可改 |
| ③ 查询数据 | 条件编译为**参数化 SQL** 打到 MySQL `ads_inst_search` | 全部机构名与数字来自查询结果 |
| ④ 看结果 | KPI + 分页清单 + 地图撒点 + 5 种排序；说"统计/分布/构成"则切换到维度统计（图表 + 分组 KPI） | 两个通道共用同一条结果链 |
| ⑤ 兜底 | 规则零命中时才问 Agnes，且提示词写死"只输出条件，不许输出机构名与数字" | 大模型故障不影响任何主路径 |

**词表单一真源**：词表只有一份正本（`web/nlq.py` 中的常量），由 `etl/export_nlq_lexicon.py` 导出为
`web/nlq_lexicon.json`（10.1 KB）并内联进单文件产物，**禁止手抄**。
实测导出口径：行政区 17 / 等级 4 / 机构类型 10 / 所有制 3 / 来源规则 4 / 科室别名 34。

### 3.3 安全边界：医疗输入硬拒答

这是本轮最刚性的一条。判定分两层：

- **词表层**：`MEDICAL_WORDS` **129 个**病征/疾病/就诊诉求词（只收词组，避免误伤"疾病预防控制中心"这类机构名）。
- **叙述层（兜底）**：出现「人群词（14 个，如"岁""老人""孩子"）+ 不适/病程词（21 个，如"困难""严重""反复"）」，
  且全文没有任何机构筛选词时，判定为病征描述。

命中即返回固定拒答文案，**不产生任何结果行**：

> 当前系统用于北京医疗机构**资源数据的查询与筛选**，不提供疾病诊断、用药建议或治疗推荐——
> 本项目的数据集里没有患者诊疗数据，也不做医学知识问答。
> 您可以改为描述想查找的机构条件，例如行政区、机构类型、医院等级、所有制、数据来源或具体科室。

拒答文案由后端与前端共用一个来源，**双端逐字一致**（`etl/verify_offline_nlq.py` 断言覆盖）。

### 3.4 数据可信度：所有数字都来自真实查询

- **后端形态**：所有接口实时查 MySQL（`ads_inst_search` 9,789 行 + DWD/DWS 服务副本）。
- **单文件形态**：数字来自内联快照，而该快照由 `web/build_spa.sh` **在构建时从 MySQL 全量拉取**（7.48 MB），
  并与 Spark 数仓产物同源；三份产物内联快照的哈希必须一致，且与后端查询结果逐项比对（150 项断言）。
- **清理掉的模拟数据**：删除了候诊状态/号源参考的模拟渲染函数（`_unusedStatusHTML`）、机构详情的"实时状态"区块，
  以及"114 挂号"快捷按钮（改为「地图导航」）。
- **说明性文案与统计数字严格区分**：关于页的清洗流程、技术栈等是说明文字；**凡是数量、分布、占比，一律取自数据库或快照字段**，
  前端不做任何本地计算替代。

### 3.5 大数据链路的真实性加固（本轮修复两处真实缺陷）

链路本身（治理 CSV → HDFS ODS → Spark 分层与五维分析 → MySQL ADS → Flask → 前端）在 2026-09-15 已贯通。
本轮在**真跑**过程中暴露并修复了两个此前潜伏的数据缺陷：

**(1) 机构类型归一化缺 3 个分支（影响 3,463 家机构）**

`spark/jobs/layer_dwd.py` 的 `category_norm` 只覆盖到"体检中心"，导致
**社区卫生服务中心（299）／社区卫生服务站（1,205）／村卫生室（1,959）共 3,463 家**基层机构
被错误并入"其他机构"。修复后补 3 个分支：

```python
.when(F.col("category").contains("社区卫生服务中心"), "社区卫生服务中心")
.when(F.col("category").contains("社区卫生服务站"), "社区卫生服务站")
.when(F.col("category").contains("卫生室"), "村卫生室")
```

重跑 `--from dwd` 后 `dws_inst_by_category` 由 7 行 → **10 行**，与真实数据一致。

**(2) Spark 会话时区为 UTC，批次日期会偏差一天**

容器默认 `TZ=UTC`，而 Spark 的 `current_timestamp()` / `date_format` 按**会话时区**渲染。
在北京时间 00:00–08:00 跑批时，UTC 日期还停在前一天，`ads_etl_snapshot.batch_date` 会写进昨天，
前端「快照 &lt;日期&gt;」跟着出错。修复：在 `spark/jobs/common.py` 显式固定
`spark.sql.session.timeZone = Asia/Shanghai`。

**修复实测**（同一台机器，修复前后各跑一次 `--from time`）：

| | batch_ts 写入值 | 说明 |
|---|---|---|
| 修复前 | `2026-09-20 01:23:54` | UTC，与北京时差 8 小时 |
| 修复后 | `2026-09-20 09:41:03` | 北京时间，与宿主 `date` 一致 ✅ |

## 六、附录：答辩口径速查

| 问题 | 一句话答案 |
|---|---|
| 系统做什么？ | 把北京 9,789 家医疗机构的公开资源数据整合起来，支持用一句话或条件组合筛选、统计、对比、看分布 |

| AI 在这里干什么？ | 只把中文说法翻译成筛选条件（如"朝阳和海淀的三级医院" → 行政区 + 等级条件卡），不产生任何数字与机构名；规则引擎是主路径，大模型仅零命中兜底 |
| 数字可信吗？ | 全部来自真实查询：后端实时查 MySQL，单文件形态用 Spark 导出的内联快照，双端 150 项断言逐字段一致；前端不硬编码任何统计数字 |
