# 基于 Spark 的北京市医院医疗资源整合与智能筛选可视化系统设计与实现

## 摘要

本研究面向北京市医疗资源分布不均、公众获取机构信息渠道分散的现实问题，设计并实现了基于 Spark 的北京市医院医疗资源整合与智能筛选可视化系统。系统以北京市卫生健康委员会等公开渠道发布的医疗机构登记数据为基础，整合 70 个异构 CSV/XLSX 数据文件，构建出覆盖 9,789 家医疗机构的统一主表，并扩展了 32 个标准科室的字典与 9,335 家机构共 16,251 条科室映射关系。在数据加工层，系统采用 Apache Spark 3.5.3 作为分布式计算引擎，通过 Docker Compose 部署的 Standalone 模式集群，将原始数据按 ODS、DWD、DWS、ADS 四层模型进行离线处理，结果落地至 MySQL 8.0。在应用层，系统基于 Flask 提供 RESTful API，支持区域、医院等级、机构类型、临床科室以及基于 Haversine 公式的距离半径五个维度的组合查询，并提供距离、等级、床位规模、科室规模与综合加权评分五种排序策略；前端采用 ECharts 实现多维数据可视化，并支持构建零外部依赖的单文件离线大屏。系统的部署、运行与测试均基于 Mac M1（Apple Silicon，arm64）平台原生环境验证。测试结果显示，系统可完成 9,789 家机构的筛选与排序响应，主要接口平均响应时间在 80 ms 以内。

**关键词**：Spark；医疗资源整合；多维筛选；数据仓库分层；ECharts

## Abstract

This study designs and implements a Spark-based medical resource integration and intelligent filtering visualization system for Beijing, addressing the uneven distribution of medical resources and the fragmentation of public access to hospital information. The system integrates 70 heterogeneous CSV and XLSX files from publicly available sources, constructs a unified master table covering 9,789 medical institutions, and expands a department dictionary of 32 standard departments with 16,251 mappings across 9,335 institutions. Data processing is carried out on an Apache Spark 3.5.3 Standalone cluster deployed via Docker Compose, with the original data organized into ODS, DWD, DWS, and ADS layers, and results loaded into MySQL 8.0. The Flask-based API supports combined filtering across five dimensions: district, level, institution type, clinical department, and Haversine distance, as well as five ranking strategies (distance, level, beds, department scale, and weighted score). The front-end is built with ECharts for visualization, and can be packaged into a self-contained single-file offline dashboard. The deployment and testing are validated on a Mac M1 (arm64) platform. Experiments show that the average response time of the main APIs is within 80 ms for filtering and ranking queries over 9,789 institutions.

**Keywords**: Spark; Medical Resource Integration; Multi-dimensional Filtering; Data Warehouse Layering; ECharts

## 第 1 章 绪论

### 1.1 研究背景与意义

医疗资源是城市公共服务体系的重要组成部分，其空间分布与服务能力直接影响居民的就医可及性。截至 2024 年，北京市常住人口已超过 2,100 万，登记在册的医疗机构超过 9,800 家，但优质医疗资源在三甲医院层面过度集中于中心城区——东城、西城、海淀、朝阳四个区集中了全市 70% 以上的三级医院，而怀柔、平谷、延庆、门头沟等远郊区在特定专科上的可及性相对有限。与此同时，公众在选择就诊机构时往往依赖商业挂号平台或社交口碑，这些渠道在数据完整度、客观性与对比维度上存在局限，难以满足"先比较、再决策"的需求。

另一方面，卫生健康行政部门、各级医疗机构官网以及第三方公开平台长期沉淀了海量的机构登记信息。这些数据存在格式、编码与命名的显著差异，但同时也是反映城市医疗资源最直接、最权威的来源。若能将这些异构数据进行系统化的清洗整合，并配合空间、学科与服务能力的多维索引，公众就可以在不依赖商业挂号平台的情况下自主获取结构化的机构对比信息，研究人员也可以基于整合后的数据开展医疗资源分布的量化分析。

基于以上认识，本文设计并实现了一个基于 Spark 的北京市医院医疗资源整合与智能筛选可视化系统。系统从 70 个异构公开数据源出发，构造覆盖 9,789 家医疗机构的统一主表、科室字典与坐标体系，并基于 Apache Spark 构建离线数仓，将清洗结果落地到 MySQL ADS 层，最终通过 Flask 与 ECharts 提供多维筛选、可视化展示与详情查询。

与协同过滤或机器学习驱动的"智能推荐"路线不同，本文采用的"资源整合 + 多维筛选 + 排序"路线具有两个显著特点。第一，强调客观信息的完整呈现，避免在数据规模有限的情况下产生误导性推荐；第二，筛选与排序的维度对用户透明，符合公众自主决策与研究人员二次分析的双重需求。

### 1.2 国内外研究现状

医疗信息化领域的研究在近十年呈现出与大数据技术深度融合的趋势。一方面，电子病历、远程医疗与医院信息系统（HIS）的研究长期关注院内业务流程的数字化，相关成果在国际医学信息学协会（IMIA）和美国医学信息学会（AMIA）的年会中持续出现。另一方面，随着 Hadoop 和 Spark 生态的成熟，基于分布式计算处理大规模医疗数据的工作逐渐增多，研究方向包括：基于电子病历数据的疾病风险预测（如 MIMIC 数据集上的 ICU 死亡率预测研究）、基于公开医疗资源数据的城市服务能力评估、基于 Spark 的医院绩效考核指标计算、基于 Web GIS 的医疗资源空间可视化等。

在数据整合方面，已有研究普遍指出医疗数据存在多源、异构、低质量的特点，并提出了相应的清洗与对齐方法，例如基于本体的字段映射、基于规则的去重、基于概率模型的实体对齐等。但在公开数据的场景下，受限于源数据的稀疏字段（如本研究中的"床位数"完整率仅 0.4%），很多方法并不直接适用，需要结合业务规则进行二次清洗和补齐。

在产品层面，国内外已存在多种面向公众的医疗机构查询工具。例如美国 CMS 的 Hospital Compare 提供按地区、专科与服务质量的医院对比；国内则有健康通、各类挂号平台和地图搜索。这类工具通常以某一类平台数据为核心，并未对公开登记数据进行系统化的整合；同时它们大多采用推荐算法，对本科教学场景下的"可解释性"与"过程可见性"要求并不友好。

综合来看，已有研究在"医疗信息化"和"大数据处理"两个方向都积累了丰富成果，但在"将多源公开医疗登记数据系统整合并以多维筛选形式公开呈现"这一交叉点上，仍缺少面向公众的、轻量级的、可教学的工程实现。本研究试图在这一交叉方向上做一次探索。

### 1.3 研究内容与主要工作

本研究的主要内容包括以下五个方面：

（1）多源异构数据清洗与整合。处理 70 个异构数据文件，覆盖 CSV（含 UTF-8/GBK/GB18030 混合编码）、xlsx 以及少量分号分隔文本，构建去重统一后的 9,789 家机构主表。

（2）地理编码与坐标体系。通过高德开放平台 Web API 批量获取 9,789 家机构的经纬度，并按精度分级（高精度 / 粗精度 / 缺失）建立可用坐标子集。

（3）科室字典构建。基于 68 家医院的国家级临床重点专科记录（主表 feature 字段权威口径）、机构登记科目与"医院等级 × 机构类型"规则，构建 32 个标准科室的字典与 16,251 条医院-科室映射。

（4）基于 PySpark 的离线数仓分层计算。按 ODS、DWD、DWS、ADS 四层模型实现 ETL，结果写入 MySQL 8.0。

（5）应用层实现。基于 Flask 的多维筛选排序 RESTful API 与基于 ECharts 的可视化大屏，提供机构详情查询与资源分布统计展示。

## 第 2 章 相关技术介绍

### 2.1 Apache Spark

Apache Spark 是一个开源的分布式计算框架，最初由加州大学伯克利分校 AMPLab 开发，2014 年成为 Apache 顶级项目。其核心抽象是弹性分布式数据集（Resilient Distributed Dataset, RDD）和基于 RDD 构建的 DataFrame、Dataset API。Spark 通过将计算任务分解为有向无环图（DAG），并由 DAG Scheduler 进行阶段切分，可实现比 Hadoop MapReduce 更高的执行效率。

Spark 的核心特点包括：①内存计算——中间结果保留在内存中，避免频繁读写 HDFS，适合迭代式机器学习与交互式查询；②多语言支持——原生支持 Scala、Java、Python（PySpark）和 R；③丰富的库生态——Spark SQL、Spark Streaming、MLlib 与 GraphX 构成完整的应用栈；④多种运行模式——Local、Standalone、YARN、Mesos 和 Kubernetes。

本研究采用 Spark 3.5.3 的 Python API（PySpark），运行于 Standalone 集群模式。Standalone 模式由 Spark 自带的 Master 与 Worker 进程组成，部署简单，适合中小规模数据处理和教学场景。Spark 3.5.3 官方 Docker 镜像（apache/spark:3.5.3）原生支持 linux/arm64，符合本研究在 Mac M1 平台上的运行要求。

### 2.2 数据仓库分层模型

数据仓库的"分层建模"思想最早由数据仓库之父 Bill Inmon 与 Ralph Kimball 分别从不同角度提出，已成为离线数仓的标准实践。本文借鉴了业界主流的 ODS-DWS-DWS-ADS 四层架构：①ODS 层（Operational Data Store，操作数据层）保留原始数据，字段与源数据保持一致；②DWD 层（Data Warehouse Detail，明细层）对 ODS 层数据进行清洗、标准化和关联，建立主题宽表；③DWS 层（Data Warehouse Summary，汇总层）在 DWD 基础上按业务维度做轻度聚合，供主题分析；④ADS 层（Application Data Store，应用层）面向具体应用，存放可以直接被前端调用的结果表。

这种分层设计在工业界有广泛实践，其优势在于：层次清晰、职责单一、便于数据血缘追踪与回溯。本研究的数据规模虽然有限（万级机构），但完整的四层结构对教学与方法迁移具有同样价值。

### 2.3 Docker 与 Docker Compose

Docker 是一种轻量级的操作系统级虚拟化技术，通过命名空间和控制组实现进程隔离，使应用程序及其依赖被打包为标准化的"镜像"，并在任何支持 Docker 的平台上以"容器"形式运行。本研究的 Spark 集群和 MySQL 数据库均通过 Docker 容器部署，避免了在宿主机的复杂依赖配置。

Docker Compose 是 Docker 官方提供的多容器编排工具，通过 YAML 文件描述服务（service）的镜像、网络、端口、卷挂载和环境变量关系。使用 `docker compose up -d` 命令可以在数秒内启动完整的开发环境。本研究的 docker-compose.yml 定义了三个服务：spark-master（apache/spark:3.5.3 镜像，运行 Master 进程）；spark-worker（同镜像，运行 Worker 进程，4 核 4 GB）；hospital-mysql（mysql:8.0 镜像，运行 MySQL 服务）。通过 volumes 配置，宿主机的 data/ 目录以只读方式挂载到容器的 /opt/workspace/data 目录，spark/ 目录挂载到 /opt/workspace/jobs 目录，使 Spark 作业可以直接访问本地数据并提交运行。

### 2.4 MySQL

MySQL 是当前最流行的开源关系型数据库之一，在 Web 应用、数据仓库和 OLAP 场景下均有广泛应用。MySQL 8.0 引入了窗口函数、CTE（公用表表达式）和默认字符集 utf8mb4 等特性，使其在处理复杂查询时更加灵活。

在本研究中，MySQL 8.0 承担了 ADS 层（应用层）的存储职责，接收来自 Spark ETL 作业的最终结果表，供 Flask 后端进行低延迟的筛选和统计查询。考虑到 ADS 表的数据量（万级）和查询模式（带索引的范围查询、聚合查询），MySQL 的性能完全够用。

### 2.5 Flask Web 框架

Flask 是一个用 Python 编写的轻量级 Web 框架，基于 Werkzeug WSGI 工具集和 Jinja2 模板引擎。Flask 以"微框架"著称，核心只包含路由、请求处理和模板渲染，通过扩展可以快速加入 ORM、表单、认证、RESTful API 等功能。

本研究使用 Flask 作为后端框架，主要任务是定义筛选、详情、概览三类 API。Flask 本身只负责路由与 JSON 序列化，复杂的 SQL 拼接通过 SQLAlchemy 配合 PyMySQL 实现。

### 2.6 ECharts

ECharts 是由百度开源、目前由 Apache 基金会孵化的一款数据可视化图表库，支持折线图、柱状图、饼图、散点图、热力图、地图、雷达图、桑基图等近 30 种图表类型，并支持动画、Tooltip、Legend 等交互功能。ECharts 通过 JavaScript 在浏览器端渲染，无需服务端渲染，适合中大规模数据的快速可视化展示。本研究使用 ECharts 实现区域机构数量分布柱状图、机构等级分布饼图、科室覆盖度横向条形图与高德地图标注。

### 2.7 高德开放平台 Web 服务

高德开放平台是国内常用的地图与位置服务供应商，其 Web 服务 API 提供地理编码（地址→经纬度）、逆地理编码（经纬度→地址）、路径规划、POI 搜索等功能。开发者通过个人实名认证可以免费使用 Web 服务 API，每日调用上限为 5,000 次。本研究使用其地理编码接口，将 9,789 家机构的地址转换为经纬度。由于个人Key存在 5,000 次/天的限制，本研究设计了批量地理编码与断点续跑机制，将编码任务拆分为多次运行，每次只处理当日新配额内的记录，避免了单次运行失败导致的进度丢失。

## 第 3 章 系统需求分析与总体设计

### 3.1 需求分析

#### 3.1.1 功能性需求

本研究的核心功能是提供一个基于北京市医疗资源整合结果的多维筛选与排序工具，辅助公众和研究人员快速定位目标机构。结合实际使用场景，系统应具备以下功能：

（1）多维筛选。用户可以按行政区、医院等级（一级、二级、三级、未定级）、机构类型（综合医院、中医医院、专科医院、诊所、门诊部、村卫生室、社区卫生服务中心、医务室、急救机构等）、临床科室（内科、外科、妇产科、儿科等 32 个标准科室）和距离半径（基于 Haversine 公式计算）进行组合筛选。

（2）多策略排序。在筛选结果的基础上，用户可选择按距离升序、医院等级降序、床位规模降序、科室规模降序或综合加权评分降序五种排序策略。

（3）机构详情。点击列表中的机构，可以查看机构的完整信息（地址、电话、邮编、科室列表、坐标、登记类别等）。

（4）可视化大屏。系统提供若干统计图表（区域分布、等级分布、科室覆盖度等）以辅助决策和直观展示。

#### 3.1.2 非功能性需求

除功能性需求外，系统还应满足以下非功能性需求：

（1）查询性能。基于 9,789 家机构的数据规模，筛选排序请求应在 200 ms 内返回。

（2）可移植性。系统应能在主流操作系统（macOS、Linux、Windows）上一键部署。

（3）可扩展性。数据处理层应支持新增数据源的接入，数仓分层结构应便于新增分析维度。

（4）可维护性。代码应有清晰的模块划分和注释，便于二次开发。

#### 3.1.3 数据需求

数据需求方面，本研究的数据全部来自公开渠道，主要包括：①北京市卫生健康委员会及下属区卫健委公开的医疗机构登记数据；②北京市医保定点医疗机构名录；③北京市中医医疗机构名录（含一级、二级、三级）；④部分区/市统计公报中的卫生资源数据；⑤国家卫健委发布的临床重点专科名单。数据量约 70 个文件，原始记录约 13,803 条，经清洗整合后主表为 9,789 家机构。

### 3.2 系统总体架构

系统采用经典的"数据源-数据处理-数据服务-数据应用"四层架构，整体架构图如图 3.1 所示。

数据流说明：
- 多源 CSV/XLSX 文件 → 数据清洗整合脚本（clean_merge.py）→ 主表 master_institutions.csv
- 主表 + 地址 → 地理编码脚本（geocode_amap.py）→ 地理编码缓存 geocode_cache.csv

- hospital-mysql：MySQL 8.0 服务，对外暴露端口 3307（宿主机 3306 已被本机 MySQL 服务占用，因此容器映射为 3307）。

## 第 4 章 系统详细实现

### 4.1 多源异构数据采集与整合

#### 4.1.1 数据源情况

本研究的数据全部来自公开渠道，共 70 个数据文件，文件格式和编码情况如下：文件格式上，CSV 为主（66 个），少量 xlsx（4 个）；字符编码上，UTF-8（带 BOM 和不带 BOM）、GBK、GB18030 混合；分隔符上，大部分为英文逗号，少量为分号；表头上，大部分在第一行，少部分文件含大标题行或落款行；字段命名上，"机构名称"在 70 个文件中出现了 7 种不同的命名。

#### 4.1.2 格式自适应读取

由于数据格式混杂，本研究在 clean_merge.py 中实现了 load_any 函数，对每种格式进行识别：

```python
def load_any(path):
    with open(path, "rb") as f:
        head = f.read(8)
    if head[:2] == b"PK":                       # xlsx（含伪装成 .csv 的）
        return _load_xlsx(path)
    if head[:4] == b"\xd0\xcf\x11\xe0":         # 老版 xls（OLE2）
        return _load_xls(path)
    return _load_text(path)
```

该函数通过读取文件头部的魔数判断真实格式，避免被文件扩展名误导。其中，通州某 xlsx 文件声明的维度为 1048542 × 16331（明显异常），通过 `ws.reset_dimensions()` 重置维度并按实际内容迭代，避免了 openpyxl 按声明维度加载导致的 OOM。

#### 4.1.3 编码自适应

针对 UTF-8/GBK/GB18030 三种编码混杂的情况，本研究实现了"utf-8-sig → gbk → gb18030"的级联尝试链：

```python
for enc in ("utf-8-sig", "gbk", "gb18030"):
    try:
        df = pd.read_csv(path, encoding=enc)
        return df
    except UnicodeDecodeError:
        continue
```

#### 4.1.4 去重合并策略

原始数据中存在大量同一机构的多源重复记录（最高同一机构被 9 个来源同时收录）。本研究采用"名称规范化 + 字段丰富度合并 + src_count 多源计数"的策略：

第一步，对机构名称做规范化处理：去除全角/半角空格、统一括号（半角 → 全角）、去除"北京市"前缀、去除"医院/诊所/门诊部"等后缀差异，使来自不同来源的同一机构名称归并为同一键。

第二步，以规范化名称作为归并键，按字段丰富度择优合并：例如 A 来源提供了 addr 和 phone，B 来源只提供了 name，则合并后保留 A 的更丰富字段。

第三步，记录 src_count 多源交叉验证次数：原始 13,803 条记录经归并后变为 9,789 家机构（后期治理又合并了 2 家镜像机构记录），其中 3,139 个机构名涉及多来源重复，657 家（6.7%）的 src_count ≥ 3，可信度较高。

#### 4.1.5 等级编码统一

原始数据的等级取值共 25 种以上，包括"三级甲等"、"3-三级"、"三级甲等综合"、"三级甲等心血管病专科"、"未定级"、"未评级"、"无等级"、"1-一级"、"一级无等"等多种写法。本研究将其统一归一化为"一级/二级/三级/未定级"4 个主等级，并在 PySpark 中通过 when-otherwise 表达式完成归一化：

```python
.withColumn("level_norm",
    F.when(F.col("grade_scope") == "not_applicable", F.lit("不适用医院分级"))
     .when(F.col("level").isin("三级", "三级甲等", "三级乙等", "三级丙等"), F.lit("三级"))
     .when(F.col("level").isin("二级", "二级甲等", "二级乙等", "二级丙等"), F.lit("二级"))
     .when(F.col("level").isin("一级", "一级甲等", "一级乙等", "一级丙等"), F.lit("一级"))
     .otherwise(F.lit("未定级")))
```

#### 4.1.6 等级统计口径治理

在数据探查中发现一个容易被忽视、却会直接误导可视化结论的问题：**"医院等级"并非所有医疗机构的属性**。我国《医院评审暂行办法》规定的一级、二级、三级评审，其对象是承担住院服务的医院类机构；而诊所、村卫生室、门诊部、社区卫生服务中心（站）、医务室、急救机构、疾病预防控制机构、体检机构等，在制度上并不参加医院等级评审，天然不具备"一级/二级/三级"取值。

若采用 `otherwise(lit("未定级"))` 的朴素归一化，这 8,502 家不参评机构会被全部计入"未定级"，使等级分布中出现占比 87.2% 的假性未定级，不仅掩盖真实的等级结构，也会让"未定级"这一标签在语义上同时表示"应参评但数据缺失"与"本就不适用"两种完全不同的含义。

为此本研究引入 `grade_scope` 字段标识机构是否适用医院等级评审，判定规则按优先级短路执行，见表 4-x。

| 优先级 | 判定条件 | grade_scope | 说明 |
| --- | --- | --- | --- |
| 1 | level 字段非空 | applicable | 已有等级记录，必属参评机构 |
| 2 | category/category_raw 属住院医院类（综合医院、中医医院、妇幼保健院、中西医结合医院、疗养院等） | applicable | 制度上必须参加评审 |
| 3 | 机构名称含"医院"且非下属分支（不含医务室/门诊部/诊所/服务站/服务中心/体检等后缀） | applicable | 名称回补，修正类别字段缺失 |
| 4 | 类别为诊所、村卫生室、门诊部、社区卫生服务中心（站）、医务室、急救机构、公共卫生机构、护理站、体检机构、其他医疗机构 | not_applicable | 不参加医院等级评审 |
| 5 | 其余 | unknown | 待人工确认 |

该规则由 `etl/build_grade_scope.py` 实现并支持 `--apply` 回写主表。经口径划分后，全表 9,789 家机构中 **1,287 家（13.1%）属应参评机构**，其余 8,502 家标记为"不适用医院分级"。应参评机构内部的等级分布为：一级 832 家（64.6%）、二级 223 家（17.3%）、三级 202 家（15.7%）、未定级 30 家（2.3%）。

口径治理带来三点收益：其一，"未定级"占比由 87.2% 降至 2.3%，等级分布恢复可读性；其二，修正了 487 家"有等级却被归入门诊部/社区卫生服务中心类"的机构（多为"××社区卫生服务中心（××医院）"一块牌子两套名称的情形），使其回到应参评口径；其三，前端与接口均以 `grade_scope` 为过滤条件，避免不参评机构污染等级筛选与等级分布图。

#### 4.1.7 区名清洗

原始数据中存在"北京昌平区"、"北京市朝阳区"等冗余前缀，本研究通过 Python 的正则替换和 PySpark 的 `substring` 函数修正为标准区名。清洗后，district 字段完整率从 99.2% 提升到 **100%**（治理前 41 家"空 district"通过 addr 自动推断+人工修正已全部归位）。

### 4.2 地理编码与坐标体系

#### 4.2.1 高德 Web 服务 API

本研究使用高德开放平台的地理编码 API 将 9,789 家机构的地址转换为经纬度。个人开发者免费额度为 5,000 次/天，而机构总数超过单日配额，因此本研究设计了批量断点续跑机制，将编码任务拆分为多次运行。

#### 4.2.2 编码脚本实现

geocode_amap.py 通过读入 `data/.amap_key.txt` 中的 Key，按机构 id 逐条调用 API，并将结果按 id 增量写入 `geocode_cache.csv`。脚本支持断点续跑：启动时先读取缓存中已有的 id 集合，仅对集合外的机构发起请求；当缓存文件不存在或某机构 id 缺失时，重新发起请求。脚本同时实现了 QPS 限流（请求间隔 0.15 s）与每日额度控制（--limit 参数限制本次运行最多新编码条数）。这一设计保证了任务可以分多次跨天执行而不会丢失进度。

#### 4.2.3 编码降级链路

本研究设计了"详细地址 → 区+机构名 → 标记 failed"的降级链路：

```python
def make_addr(rec):
    addr = (rec.get("addr") or "").strip()
    if addr and len(addr) > 5:
        return addr
    district = (rec.get("district") or "").strip()
    name = (rec.get("name") or "").strip()
    if district and name:
        return f"{district}{name}"
    return None  # failed，留待人工
```

通过该链路，约 30% 仅登记了"区+机构名"而没有详细地址的机构得以成功编码。

#### 4.2.4 精度分级

高德 API 返回的 level 字段包含"门址"、"兴趣点"、"道路"、"住宅区"、"村庄"、"区县"等 10 余种精度，本研究将其归一化为 3 个精度桶：high（高精度，门址/门牌号/兴趣点）、rough（粗精度，道路/住宅区/村庄/乡镇/区县/公交地铁站点等）、missing（缺失或编码失败）。该分级直接写入 ads_inst_search 表的 coord_precision 字段，供前端在筛选时做提示：high 精度的机构在地图上可精确标注，rough 精度的机构仅参与距离筛选并在地图上正常展示（其坐标可能落在区级中心），missing 精度的机构不出现在地图与距离筛选中。

### 4.3 科室字典构建

#### 4.3.1 数据来源优先级

本研究科室字典的来源按可信度从高到低分为 4 层：

（1）国家级临床重点专科记录（主表 feature 字段中 feature_level='1' 的权威口径，共 68 家医院）；
（2）机构登记的真实诊疗科目（key_depts 字段，1,793 条）；
（3）机构名称关键词推断（如"XX 口腔诊所"→口腔科，3,886 条）；
（4）"医院等级 × 机构类型"规则推导（10,611 条，主要用于诊所、门诊部、村卫生室等无登记信息的基层机构）。

覆盖 9,335 / 9,789 家机构，共 16,251 条医院-科室映射。未覆盖的 454 家主要是体检中心、疾控中心、医疗美容机构，其本身并不开展临床诊疗，留空是合理的设计选择。

#### 4.3.2 标准科室分类

本研究共定义 32 个标准科室，归入 11 个一级大类：内科（10 个）、外科（6 个）、妇产科儿科（2 个）、肿瘤科（1 个）、精神心理科（1 个）、五官科（3 个）、皮肤科（1 个）、中医科（3 个）、感染科（2 个）、急诊重症（2 个）、康复科（1 个）。

#### 4.3.3 关键词到标准的映射

针对中医特色病种（如"脾胃病"、"肺病"、"脑病"）与西医科室（如"心血管内科"、"神经内科"）的命名差异，本研究设计了带优先级的 SYNONYMS 列表，按"先具体后泛化"的顺序匹配。例如对"心血管科"先匹配到"心血管内科"，对"内科"才泛化匹配到"普内科"，从而避免过度泛化。

#### 4.3.4 质量验证

对协和医院、北京儿童医院、广安门医院、北京佑安医院等知名医院做了重点抽检，结果显示重点专科标记正确，未出现错配。说明基于优先级字典的科室识别流程达到了设计要求。

此外，重点专科数据经历了一次口径同步问题的修复：早期版本的专科数据源采用医院-科室映射表中的 is_key_specialty 标记，仅覆盖 20 家医院，与主表 feature 字段（权威口径，68 家）不一致。最终实现将 ADS 层的 ads_specialty_hospital 表改为直接从 DWD 层 feature 字段（feature_level='1'）经分号切分展开生成，得到 418 条专科-医院映射，两套口径完全统一。该问题也提示了数仓开发中"同一业务概念存在多个数据出口"时必须显式声明权威数据源（Single Source of Truth）的重要性。

### 4.4 基于 PySpark 的数仓分层实现

#### 4.4.1 集群拓扑

Spark 集群采用Standalone模式，由 1 个 Master 和 1 个 Worker 节点组成。Worker 节点配置 4 核 CPU 和 4 GB 堆内存，足以处理万级机构的数据。Master 节点负责作业调度，Worker 节点负责实际计算。Master 与 Worker 通过 spark://spark-master:7077 协议通信。

#### 4.4.2 作业提交流程

作业通过 `docker exec spark-master /opt/spark/bin/spark-submit` 命令提交，关键参数包括：--master spark://spark-master:7077 指定 Master 地址；--jars 与 --driver-class-path 同时指定 mysql-connector-j-8.4.0.jar 用于 MySQL 写入；作业脚本路径为容器内的 /opt/workspace/jobs/etl_hospital.py。

#### 4.4.3 数仓分层实现

本研究的数仓分层实现集中在 spark/etl_hospital.py 中，按照"ODS（原始落库）→ DWD（清洗关联）→ DWS（多维汇总）→ ADS（应用表）"的顺序实现。代码整体结构清晰，主体函数分为 print_section（章节标题打印）、write_mysql（DataFrame 写入 MySQL 工具函数）和 main（主流程）三部分。其中 DWD 层的核心是坐标关联与等级归一化，DWS 层的核心是 groupBy 聚合，ADS 层的核心是按业务场景裁剪字段。

#### 4.4.4 关键数据快照

完成数仓分层后，从 ADS 层取样得到以下结果：
- 按行政区：昌平 1,295 家、朝阳 1,169 家、房山 1,077 家、顺义 978 家、大兴 877 家、西城 730 家、海淀 696 家、密云 687 家、丰台 530 家；
- 按等级（仅统计应参评机构 1,287 家）：一级 832 家（64.6%）、二级 223 家（17.3%）、三级 202 家（15.7%）、未定级 30 家（2.3%）；另有 8,502 家机构不参加医院等级评审，单列"不适用医院分级"（详见 4.1.6 节口径治理）；
- 科室覆盖：全科医疗科 4,412 家、普内科 2,295 家、中医内科 2,098 家、口腔科 1,769 家（dws_dept_coverage 共 29 个有覆盖数据的科室）；
- 重点专科：68 家医院、418 条专科-医院映射（feature 权威口径，见 4.3.4 节）。

### 4.5 床位与科室规模指标

#### 4.5.1 指标现状与处理思路

原始数据中"日均门急诊量"、"床位使用率"、"医生数"等负载指标完全缺失（原始床位数完整率仅 0.4%），无法直接支撑排序需求。本研究没有采用虚构模拟数据的方式，而是采取两条路径：其一，通过 `etl/enrich_level_beds.py` 构建多源证据池，从登记数据中匹配真实床位记录回填（当前已回填 122 家，采用"预览—复核—应用"三段式流程，默认只生成建议清单，`--apply` 才写回主表，避免未经复核的污染）；其二，排序公式对缺失字段按最小值处理，使缺失床位的机构不获得床位分项加分，保证排序在数据稀疏条件下仍然可用。

#### 4.5.2 数据使用声明

床位等规模字段的完整率目前仍有限（1.2%），因此综合评分排序结果应理解为"以等级与距离为主导、规模指标为辅助参考"的排序；用户也可切换为纯距离或纯等级排序。本研究在文档与接口注释中明确标注了各字段的来源与完整率，避免使用者在数据稀疏条件下过度解读排序结果。

### 4.6 筛选排序服务实现

#### 4.6.1 Flask 应用结构

Flask 应用位于 web/ 目录下，采用单文件后端结构：app.py 集中承担 Flask 实例化、路由注册与数据库连接配置（DB_CONFIG），共提供 7 个接口——多维筛选排序、机构详情（关联科室明细）、区域/等级/科室概览、重点专科、筛选项元数据与健康检查；templates/index.html 与 static/（本地化的 echarts.min.js、beijing.json）负责前端页面与静态资源。此外，目录内的 build_spa.sh 可将数据库当前状态导出为快照 JSON 并注入页面，构建出零外部依赖的单文件离线大屏（详见 4.7.6 节）。

#### 4.6.2 Haversine 距离计算

Haversine 公式根据两点的经纬度计算球面距离（单位千米），公式如下：

```
a = sin²(Δφ/2) + cos φ1 · cos φ2 · sin²(Δλ/2)
c = 2 · atan2(√a, √(1−a))
d = R · c   (R = 6,371 km)
```

本研究将 Haversine 计算下推到 MySQL，使用 SQL 函数实现：

```sql
ROUND(
  6371 * 2 * ASIN(
    SQRT(
      POWER(SIN(RADIANS((lat - :user_lat) / 2)), 2) +
      COS(RADIANS(:user_lat)) * COS(RADIANS(lat)) *
      POWER(SIN(RADIANS((lng - :user_lng) / 2)), 2)
    )
  ), 2
) AS distance_km
```

#### 4.6.3 多条件组合筛选 SQL

筛选接口根据传入参数动态拼接 WHERE 子句，支持行政区、医院等级、机构类型、临床科室、距离半径五个维度的任意组合。距离计算通过子查询先对全表计算 Haversine 距离再与主表按 id 关联（有坐标的机构才计算距离），评分表达式随查询一并生成。核心 SQL 结构如下（节选自 app.py 实际实现）：

```sql
SELECT t.id, t.name, t.district, t.level_norm, t.beds, t.dept_count,
       t.key_specialty_count, d.distance_km,
       -- 加权评分 = 0.4*等级 + 0.3*距离 + 0.2*床位 + 0.1*科室规模
       ROUND(0.4 * (CASE t.level_norm WHEN '三级' THEN 3 WHEN '二级' THEN 2
                                      WHEN '一级' THEN 1 ELSE 0.5 END) / 3
           + 0.3 * (1 - LEAST(IFNULL(d.distance_km, 60) / 60, 1))
           + 0.2 * LEAST(IFNULL(t.beds, 0) / 1500, 1)
           + 0.1 * LEAST(IFNULL(t.dept_count, 0) / 30, 1), 4) AS score
FROM ads_inst_search t
JOIN (SELECT id,
        CASE WHEN lng IS NOT NULL AND lat IS NOT NULL THEN
          ROUND(6371 * 2 * ASIN(SQRT(
            POWER(SIN(RADIANS(lat - %s) / 2), 2) +
            COS(RADIANS(%s)) * COS(RADIANS(lat)) *
            POWER(SIN(RADIANS(lng - %s) / 2), 2))), 2)
        ELSE NULL END AS distance_km
      FROM ads_inst_search) d ON t.id = d.id
WHERE {动态拼接的条件}
ORDER BY {按排序策略生成} LIMIT %s OFFSET %s;
```

科室维度筛选通过 EXISTS 子查询关联 DWD 层科室映射表实现；等级筛选自动附加 `grade_scope='applicable'` 条件，保证"不适用医院分级"的机构不进入等级筛选结果。

#### 4.6.4 多策略排序与加权评分

排序策略包括五种：距离升序（distance，无坐标机构排最后）、等级降序（level，三级/二级/一级映射 3/2/1）、床位规模降序（beds）、科室规模降序（depts）与综合加权评分降序（score，默认）。其中综合评分采用加权公式：

score = 0.4 × 等级分 + 0.3 × 距离分 + 0.2 × 床位分 + 0.1 × 科室分

各分项均归一化到 [0,1]：等级分按三级/二级/一级/其他映射为 3/2/1/0.5 再除以 3；距离分按 1 − min(距离/60, 1) 计算（60 千米外为 0 分，无坐标机构同样计 0 分）；床位分按 min(床位数/1500, 1) 计算（缺失按 0 处理）；科室分按 min(科室数/30, 1) 计算。权重的设定参考了通用就诊决策习惯：等级与距离是首要因素，床位与科室规模是服务能力的次要代理指标。相比引入虚构的"负载"指标，该设计在数据稀疏条件下（床位完整率仅 1.2%）仍能给出可解释、可复现的排序结果。

3. **朝阳区精细比对最可信**：官方 2024 末数据完整度最高（2080 家 / 三级 27），本地 1170 家 / 三级 30，三级差仅 +3 家（合理范围）。差距在基层（约 −900 家主要为诊所/卫生服务站），符合"基层覆盖度有限"的口径。

5. **三级未定等（123 家）的可信度**：包含协和、同仁、北京医院、宣武、东直门、广安门、望京等知名三甲，其 `level_sub` 字段缺失并非数据错误，而是源数据未明确"三甲/三乙/三丙"细分。本研究已在论文中说明"level_sub 字段作为治理增强项，仅当源数据明确给出时才填入"，避免误标。

#### 5.3.2 国家临床重点专科数据的联网增强

为弥补早期重点专科数据"仅含医院名称、缺乏权威级别与细分字段"的不足，本研究于 2026-09-06 通过网络爬取（WebSearch + WebFetch）对「国家临床重点专科」进行了多源交叉扩充，主要采集源如表 5.9 所示。

**表 5.9 国家临床重点专科联网采集源**

| 采集源 | 内容/覆盖 |
|---|---|
| 国家中医药管理局（北京推荐项目公示） | 中医专业国家重点专科项目，含申报单位、专科名称、负责人 |
| 国家卫生计生委「国家临床重点专科建设项目」 | 230 个重点专科项目，按专科分类排序的医院清单 |

经整合去重与规范化（`etl/build_specialty_enhanced.py`），并与主表按医院名称+别名（如"卫生部北京医院→北京医院"、"首都医科大学附属××→××"）做了匹配，最终形成：
- **43 家医院、229 条国家级临床重点专科记录**（去重后），其中与主表成功匹配 **42 家**（匹配率 99.6%，2 家为三博脑科、道培血液病等未入主表的专科医院，已通过别名映射归并）；
- 每条记录含**医院名称、专科名称、所属系统（中医/西医）、批次、负责人、地址**等字段；
- 将结果按院汇总，在主表 `master_institutions.csv` 新增 **`national_specialty`、`national_specialty_count`** 两列，并贯通至数仓 DWD→ADS 层，供前端详情浮层展示。

数据质量抽检显示：**中国医学科学院北京协和医院（28 个）、北京大学第三医院（20 个）、北京大学人民医院（18 个）、北京大学第一医院（18 个）、中日友好医院（15 个）** 等知名三甲的国家级重点专科数量与官方公开口径一致；机构详情浮层新增「国家重点专科」字段，以金色高亮展示（如图 5.1 所示）。

这一工作与 4.3.4 节的 `feature` 权威口径（68 家医院、418 条专科医院映射）形成互补：`feature` 字段为**擅长科室分级**（L1 重点专科 / L2 优势科室 / L3 诊疗科室）提供权威来源，而本次联网补充的 `national_specialty` 字段聚焦**国家级临床重点专科**认定，二者分别侧重"科室权威度分级"与"国家级专科认定"，共同强化了系统对医院学科实力的刻画能力。

此外，为消除两套口径之间的不一致，本研究又用 `national_specialty` 对 `feature` 字段做了**反向校验补全**（`etl/backfill_feature_from_national.py`）。受早期抓取源数据不全影响，`feature_level='1'` 的 68 家重点专科医院中，少数综合医院的 `feature` 字段内容稀疏（如北京医院最初仅录"老年病科"，但其实际有 9 个国家临床重点专科）。补全脚本仅针对 `feature_level='1'` 且 `national_specialty_count>0` 的 27 家医院，按专科名归一化（去括号/去"诊疗中心"后缀）后做差集，将 `national` 中存在但 `feature` 中缺失的专科按权威来源顺序追加，最终：

- **17 家医院补全了 78 条专科片段**，如北京医院（1 → 9 个）、中国医学科学院北京协和医院（18 → 35 个）、中日友好医院（24 → 32 个）、北京大学第三医院（19 → 39 个）等；
- 处理策略：专科名归一化后采用"子串包含"等价判断（如"心血管内科"与"心血管科"识别为同一科室），避免重复追加；
- 补全前后主表均备份至 `data/processed/backup/`，产物报告 `govern_report_feat_backfill.md`；
- 经 Spark ETL 重跑，`ads_specialty_hospital` 由 418 条增至 **496 条**，前端详情浮层"擅长科室"标签同步扩充，两套专科口径（`feature` 分级 + `national_specialty` 国家级认定）实现自洽统一。

### 5.4 性能测试

本研究对筛选排序 API 做了性能测试，测试方式为对同一查询连续调用 100 次取平均值与分位数（Flask 开发服务器，MySQL 容器化部署）。结果如下：
- 单一条件筛选（仅按区）：平均 39 ms（p95 = 41 ms）；
- 双条件筛选（区+等级）：平均 32 ms（p95 = 33 ms）；
- 三条件筛选（区+等级+类型）：平均 23 ms（p95 = 25 ms）；
- 全表含距离计算的查询（未加筛选条件）：平均 73 ms（p95 = 80 ms）；
- 全维度筛选 + 评分排序 + 分页：平均 23 ms（p95 = 24 ms）。

主要 API 平均响应时间均在 80 ms 以内，远优于 3.1.2 节提出的 200 ms 性能要求；其中含距离计算的查询因需对全表 9,789 行计算 Haversine 距离，耗时最长，叠加筛选条件后反而因参与计算的行数减少而更快。

## 第 6 章 总结与展望

### 6.1 工作总结

本研究设计并实现了基于 Spark 的北京市医院医疗资源整合与智能筛选可视化系统，主要完成的工作包括：
（1）整合 70 个异构数据文件，构建 9,789 家机构的统一主表；
（2）完成高德批量地理编码（覆盖率 **99.98%** = 9,787/9,789，仅 2 家地址不规范引擎无解），建立 high/rough/missing 三级坐标精度分级体系；
（3）构建 32 个标准科室的字典与 16,251 条医院-科室映射，覆盖 95.3% 的机构，重点专科采用 feature 权威口径覆盖 68 家医院；
（4）完成基于 PySpark 的离线数仓分层计算（ODS/DWD/DWS/ADS），结果落地 MySQL；
（5）实现 Flask 五维筛选 + 五种排序策略 API 与 ECharts 可视化大屏，主要 API 平均响应在 80 ms 以内；
（6）实现单文件离线大屏构建（build_spa.sh），支持无网络演示与仓库在线浏览；
（7）联网多源交叉扩充国家临床重点专科数据（43 家医院、229 条记录），新增 national_specialty 字段并在详情浮层展示；
（8）联网多源交叉扩充市/区级临床重点专科数据（五源合并去重后 **283 条记录**、**77 家医院**；中医"十四五"首批 74 + 第二批 107 项全部抓齐，另含 2018/2020 年度与 2022 年度重大疫情防治项目），新增 municipal_specialty 字段，与国家级口径共同形成三层递进的专科能力表征。

### 6.2 主要创新点

本研究的创新点包括：
（1）公开数据条件下"资源整合 + 多维筛选 + 排序"的实用路线，避免了智能推荐在数据规模有限场景下的不可靠问题；
（2）离线数仓分层模型在本科工程型项目中的完整实践，为同类项目提供了模板；
（3）坐标精度分级体系，对缺失坐标和粗精度坐标做了明确区分，提升了筛选排序的可信度；
（4）医院等级统计口径治理（grade_scope 字段区分"应参评"与"不适用"机构），解决了混合口径下等级分布失真的问题；
（5）"数据库快照 → 单文件离线大屏"的构建链路，使同一前端代码同时服务在线 API 版与零依赖离线版。

### 6.3 不足与展望

本研究的不足包括：
（1）地理编码中粗精度坐标占比仍高（55.7% 的机构仅能定位到区县级），距离排序对这部分机构的参考价值有限；
（2）床位等规模指标完整率低（1.2%），综合评分中规模分项的区分度不足，需接入更权威的床位登记数据；
（3）系统未做实时数据接入，机构信息更新存在延迟；
（4）前端功能可进一步增强（如增加用户收藏、对比等交互）。

后续工作将从上述不足出发，进一步提升系统的完整性和实用性。
